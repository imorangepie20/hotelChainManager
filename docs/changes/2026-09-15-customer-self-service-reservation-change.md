# 고객 직접 예약 변경

## 변경 이유

고객이 호텔 직원에게 별도 결제 링크를 받아야만 예약을 변경할 수 있던 흐름을 개선했다. 같은 브라우저의 예약 관리 토큰으로 예약 상세에서 날짜, 객실 유형, 요금제, 성인 및 아동 수를 직접 재견적하고 차액 정산을 시작할 수 있다.

## 구현 범위

- 예약 상세에 서버 판정 기반 `예약 변경` 진입점과 불가 사유를 표시한다.
- `/reservations/{id}/change`에서 일정과 인원을 선택하고 서버 재고·요금 견적을 조회한다.
- 추가 결제는 HttpOnly 동일 브라우저 세션으로 기존 Toss 변경 결제 화면에 연결한다.
- 차액 없음은 즉시 적용 대기로, 환불 차액은 원결제 환불 처리로 전환한다.
- 추가 결제 시작 전에는 고객이 변경 요청을 취소할 수 있다.
- 고객 요청은 직원 ID를 만들지 않고 `CUSTOMER` 출처와 변경 전후 인원을 감사 기록에 남긴다.

## 서버 권한과 안전 경계

- 고객이 보낸 금액은 확정값으로 사용하지 않는다. 요청 생성 시 예약을 잠그고 재고와 가격을 다시 계산한다.
- 예약 관리 토큰이 일치하는 예약만 견적·요청·취소할 수 있다.
- 확정 예약, 체크인 전, 객실 미배정, 활성 변경 없음 조건을 서버에서 다시 확인한다.
- 정산과 변경 적용이 끝날 때까지 원예약과 원재고를 유지한다.
- V42는 고객 견적, 요청 출처, nullable 직원 actor, 변경 전후 인원 감사 필드를 추가한다.

## 자동 검증

- API: 고객 0원·추가 결제·환불·권한·취소, 견적, hold, 승인 회귀, 정산, 적용, Toss test gateway 등 집중 테스트 50건 통과
- 웹: 고객 경로·상태·문구 계약 3개, TypeScript 검사, Vite production build 통과
- Flyway: PostgreSQL 테스트 DB에서 42개 migration 검증

## 사용자 브라우저 검증

브라우저 검증은 사용자가 수행한다.

1. 예약 상세에서 `예약 변경` 진입 및 불가 사유 확인
2. 날짜·성인·아동 변경 후 객실과 차액 조회
3. 추가 결제 후 예약 확정과 새 일정 반영
4. 차액 없음과 환불 변경의 처리 중 상태 및 완료 반영
5. 추가 결제 전 변경 요청 취소와 재고 반환
6. 새로고침 후 추가 결제 계속하기
7. 모바일 배치, 키보드 초점, 오류 안내

실제 Toss 운영 키와 실과금은 검증 범위가 아니다.
