# 본사 지점 관리 - 지점 수정 (2026-09-22)

> 상태: 작업 트리에만 있고 커밋하지 않은 상태.

## 변경 이유

`admin-menu-roadmap.md` 1번 `지점·객실 유형 관리`의 남은 항목 중 "지점 수정"을 구현했다. **본사가 지점 이름을 잘못 만들거나 브랜드가 바뀌었을 때 고칠 수단이 없었다.** 더 심각한 것은 생성 API가 이름 중복을 409로 막고 있어서, **수정 수단이 없으면 한 번 잘못 만든 지점 이름을 바로잡을 방법이 아예 없었다.**

## 서버 변경

- `PATCH /api/staff/hotels/{hotelId}`가 지점의 이름·지역·시간대를 바꾼다. `HQ_ADMIN`만 허용하고 지점 직원은 403, 잘못된 세션은 401, 멱원 키 누락은 400, 없는 지점은 404다.
- **세 필드 모두 선택이다.** 보내지 않은 필드는 현재 값을 유지한다. 이 점은 객실 유형 수정과 같은 패턴이다. 본문이 완전히 비어 있으면 400인데, 빈 PATCH가 지점을 의도하지 않게 초기화하는 것을 막는다.
- **이름을 바꿀 때만 다른 지점과의 중복을 검사한다.** 자기 자신의 현재 이름은 제외한다. `where lower(name) = lower(?) and id <> ?`로 자기 자신을 빼고, 대소문자 구분 없이 중복이면 409 `HOTEL_NAME_CONFLICT`다. 생성과 같은 규칙이다.
- **시간대를 서버가 검증한다.** `ZoneId.of`로 파싱해 보고 실패하면 400이다. 시간대는 재고 시드 시작일(지점 현지 날짜)·취소 마감 시각·운영 상태 전환의 기준이다.
- **이미 지나간 날짜는 다시 계산하지 않는다.** `inventory_day`·`rate_day`·`reservation`은 날짜를 `LocalDate`로 저장하므로 시간대를 바꿔도 행이 이동하지 않는다. 새 시간대는 그 이후의 시드·마감 판정부터 적용된다. 이 제한은 사용자가 확인해야 할 동작이라 UI 안내에 적었다.
- 멱원은 두 갈래로 동작한다. 같은 `Idempotency-Key` 재호출은 200에 `changed=false`로 같은 결과를 돌려주고, 응답 유실 뒤 새 키로 같은 내용을 보내도 `staff_id`·지점·이름·지역·시간대의 SHA-256 지문이 같아 같은 결과를 돌려준다.
- **실제로 바뀌는 값이 없으면 DB를 건드리지 않고 멱원 기록만 남긴다.** 재시도가 200으로 같은 결과를 돌려주게 한다. `changed` 필드로 값이 바뀌었는지 알려준다.
- 이력에는 바꾸기 전 이름·지역·시간대를 `previous_name`·`previous_region`·`previous_timezone`에 남긴다. 나중에 변경 이력을 조회할 때 쓴다.

## 마이그레이션 변경

- V59가 아직 이전 작업과 함께 커밋되지 않은 상태이므로 **제자리에서 수정**했다. `kind`(`CREATE`·`UPDATE`) 칼럼과 이력용 `previous_*` 칼럼을 추가하고, 유일 인덱스와 요청 지문 인덱스를 `kind`를 포함하도록 바꿨다.
- **테스트 DB에서만 발생한 부작용이 있다.** V59 원본이 이미 테스트 DB에 적용된 상태에서 내용을 바꿨기 때문에 Flyway 체크섬 불일치가 났다. `flyway_schema_history`에서 version 59 행을 지우고 `hotel_command` 표를 drop해서 깨끗하게 다시 적용했다. 이 조작은 테스트 DB만 해당하고 라이브 DB에는 영향이 없다.

## 관리자 UI 변경

- `호텔 및 객실` (`/dashboard/hotels`)의 지점을 선택기 버튼에서 **표**로 바꿨다. 각 지점의 이름·지역·시간대와 `수정` 버튼을 보여준다. 시간대가 지점의 속성으로 드러나지 않으면 본사가 재고 시드의 날짜 기준을 알 수 없다.
- 지점을 클릭하면 해당 지점의 객실 유형 목록을 아래에 불러온다. 선택한 지점은 굵은 글씨로 표시한다.
- 수정 대화상자는 현재 이름·지역·시간대로 미리 채운다. 서버 검증 실패 시 대화상자를 닫지 않고 안내를 보여준다. 다른 본사 화면과 같은 패턴이다.
- 대화상자 안내에 시간대 변경의 한계를 적었다. "이미 지나간 날짜의 재고·예약은 다시 계산하지 않는다"를 명시하지 않으면 본사가 과거 보고서가 안 바뀌는 이유를 알 수 없다.

## 검증 결과

- API `mvnw -Dtest=HotelUpdateIntegrationTest` **14건**이 종료 코드 0이다. 이름 수정·지역·시간대 수정·같은 키 재호출 200 `changed=false`·새 키 같은 내용 200·값 변동 없음 200 `changed=false`·다른 지점 이름 409·자기 이름 유지 허용·대소문자 중복 409·잘못된 시간대 400·빈 본문 400·없는 지점 404·지점 직원 403·세션 없음 401·키 누락 400을 다룬다.
- 인접 8개 suite **193건**이 종료 코드 0다(객실 유형 27·재고 16·요금 20·고객 요청 22·감사 16·운영 통계 18·직원 계정 47·지점 생성 13). V59를 수정해도 기존 영역에 영향이 없음을 확인했다.
- 관리자 `tsc --noEmit`이 종료 코드 0이고, `eslint`는 경고 3건만 낸다(`react-hooks/set-state-in-effect`, 기존 컴포넌트와 같은 패턴, 신규 1건은 이전과 동일한 effect 패턴).
- Playwright `hotel-catalog` **20건**(기존 17 + 신규 3)이 종료 코드 0이다. 새 검증은 수정→선택기 반영, 이름 중복 안내, 지점 직원에게 수정 버튼이 보이지 않음이다. 인접 6개 suite 68건도 종료 코드 0이다.

## 발견·수정한 결함

1. 대화상자를 여는 두 개의 폼이 `editTarget` 변수를 공유하고 있었다. 객실 유형 수정과 지점 수정이 같은 변수를 써서 한쪽을 열면 다른 쪽 상태가 꼬일 수 있었다. 지점 수정은 `hotelEditTarget`을 따로 만들었다.
2. **테스트 두 개가 잘못된 단정을 가지고 있었다.** 하나는 수정 API에 201을 기대했고(수정은 200), 다른 하나는 "MODIFY JEJU"라는 영문 이름이 "수정 제주"와 중복된다고 가정했다. 서버 동작은 올바르고 내 단정이 틀렸다. 대소문자 중복을 실제로 시험하려면 두 지점이 같은 이름의 다른 대소문자 표기를 가져야 한다. JEJU에 영문 이름을 주고 대소문자만 다른 이름으로 충돌을 시험했다.

## 미검증 항목

- **라이브 DB·compose 재빌드·브라우저 확인은 실행하지 않았다.** V59가 라이브에 적용되지 않았으므로 실제 수정 흐름은 사용자가 확인한다.
- **판매 중지·삭제는 이번 범위가 아니다.** 삭제는 `room_type`·`reservation`·`reservation_change_request`·`website_page_room_type`·`staff_member` 외래키가 걸려 있어 안전한 삭제 조건을 따로 설계해야 한다. 본사가 실수로 지점을 지우면 예약 이력이 끊어진다.
- **판매 중지는 별도 설계가 필요하다.** `hotel` 표에 판매 중지 칼럼이 없다. 중지하면 고객 `GET /api/availability`에서 빠져야 하고, 진행 중인 예약은 그대로 둬야 한다. 기존 예약을 건드리지 않는 조건을 정해야 한다.
- **시간대를 바꿔도 과거 날짜의 재고·예약은 이동하지 않는다.** 의도된 동작이지만, 본사가 시간대를 크게 바꾸면 과거 리포트와 일자 재고의 날짜 경계가 당시 기준과 달라 보일 수 있다. 이것이 문제가 되면 별도 보정 작업이 필요하다.
- **변경 이력을 조회하는 API·화면이 없다.** `previous_*` 칼럼은 채워지지만 아직 읽는 곳이 없다. 7번 감사 메뉴와 통합할 때 다룬다.
- **지점 이름 중복 검사가 대소문자와 공백 정규화만 한다.** 유니코드 정규화(NFC 등)는 하지 않으므로 비슷하게 보이는 다른 문자로 된 이름은 중복으로 잡히지 않는다.
