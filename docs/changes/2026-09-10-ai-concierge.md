# LangGraph AI 예약 도우미

`services/concierge`에 FastAPI와 LangGraph 기반 예약 도우미를 추가하고 Docker Compose의 `9000` 포트로 실행했다. 도우미는 지점·날짜·인원·객실 수·조식 조건을 대화 상태에 보관하고, 조건이 부족하면 필요한 항목을 묻는다. 명시 날짜, 숙박일 수, “다음 주 토요일”을 해석한다.

조건이 완성되면 Spring Boot의 호텔·판매 가능 객실 API만 조회한다. 응답된 객실 유형, 요금제, 총액, 잔여 객실을 최대 세 개까지 반환하며 예약 생성·결제·가격 계산은 수행하지 않는다. 외부 LLM 키가 없는 현재 개발 환경에서는 정해진 한국어 조건 패턴을 사용하고, LangGraph가 조건 추출·누락 확인·검색·추천 단계를 관리한다.

고객 웹의 `AI 예약 도우미`는 대화 패널을 열고, 실제 조회 후보와 총액을 표시한다. `이 조건으로 객실 검색`을 누르면 지점·날짜·인원 조건을 기존 예약 바에 적용한다. 예약 확정은 기존 객실 선택 및 테스트 결제 흐름에서만 실행된다.

초기 검증: LangGraph 조건 추출·누락 질문 테스트 3개 통과, 고객 웹 `pnpm build` 통과, `GET /health` 응답 `UP`, 9000 포트에서 속초·조식 포함 요청이 Spring API의 디럭스 오션·패밀리 스위트와 동일한 금액·잔여 객실을 반환하는 것을 확인했다. 브라우저에서 대화 패널 표시를 확인했다. 당시 대화 입력과 추천 적용의 실제 클릭 검증은 남아 있었고, 2026-09-11 조건 동기화 검증에서 headless 고객 웹으로 완료했다.

## 2026-09-11 조건 동기화와 최신 검색

고객 웹은 현재 예약 바의 지역·체크인·체크아웃·성인·아동·객실 수·조식 조건을 AI `/chat` 요청에 함께 보낸다. 예약 바가 바뀌면 이전 AI 후보와 적용 버튼을 비우며, AI의 `이 조건으로 객실 검색`은 후보를 예약 카드에 복사하지 않고 Spring `GET /api/availability`를 직접 다시 호출한다. HTTP 재조회가 성공한 뒤에만 AI 패널을 닫고, 0건이면 기존 카드·선택을 비운 채 조건에 맞는 안내를 표시한다. 실패하면 패널을 열어 두고 직접 검색 안내를 표시한다.

고객 웹의 `LatestAvailabilityRequest`는 날짜·인원·지점 변경으로 이전 availability 요청을 무효화한다. 따라서 늦게 도착한 이전 응답은 카드·선택·안내·loading 상태를 덮어쓸 수 없다. AI가 같은 조건을 적용하며 시작한 새 요청은 해당 state 반영 때문에 무효화하지 않는다.

검증: 외부 의존성을 추가하지 않은 독립 실행 요청 순서 보호 검사(TypeScript 컴파일 뒤 Node 실행), `pnpm.cmd build`, 실제 `9000 /chat`과 `4080 /api/availability`의 속초·2026-09-18~20·성인 2·조식 포함 조건 비교를 수행했다. 두 조식 포함 offer의 객실 유형·요금제·총액·잔여 객실이 일치했다. headless 실제 고객 웹에서도 `/chat` body에 현재 예약 criteria가 포함되고, 적용 뒤 새 `GET /api/availability`가 발생해 조식 포함 카드가 렌더링되는 것을 확인했다. 예약 생성·임시 확보·결제는 실행하지 않았다.

한계: 외부 LLM·정책 임베딩은 아직 연결하지 않았고, 고객 대화의 영구 E2E suite는 아직 없다. 현재 FastAPI 조건 추출은 정해진 한국어 패턴을 사용한다.
