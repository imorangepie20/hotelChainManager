# 80번 포트 제거·포트 맵 문서화

> 날짜: 2026-09-26
> 작업 트리에만 있고 커밋하지 않은 상태.

## 배경

사용자가 "80번 포트는 사용하지 마"라고 지시했다. 고객 웹 컨테이너는
nginx로 정적 파일을 서비스하는데, 이 nginx가 컨테이너 안에서 `80`을
수신하고 있었다. `80`은 외부로 노출되는 포트는 아니었지만(호스트와의
매핑은 `127.0.0.1:3110:80`), Cloudflare Public Hostname의 URL이
`web:80`이었으므로 **터널 설정값에 80이 계속 등장**했다.

포트 할당이 여러 파일에 흩어져 있었던 것도 같이 정리했다. `nginx.conf`·
`Dockerfile`·`compose.zorin.yml`·`DEPLOY-ZORIN.md`·
`set-tunnel-token.sh`이 각각 포트를 적고 있었고, 로컬 개발
(`compose.yaml`)과 배포(`compose.zorin.yml`)의 포트 체계가 서로
달랐다.

## 변경 내용

### 1. nginx 수신 포트 80 → 8080

- `apps/web/infra/nginx.conf`의 `listen 80`을 `listen 8080`로.
- `apps/web/infra/Dockerfile`의 `EXPOSE 80`을 `EXPOSE 8080`로.
- `infra/compose.zorin.yml`의 `web` 서비스:
  - 포트 매핑 `127.0.0.1:3110:80` → `127.0.0.1:3110:8080`
  - 헬스체크 `wget … http://127.0.0.1/` → `… http://127.0.0.1:8080/`

**컨테이너 내부 포트만 바꿨다.** 호스트 포트 `3110`은 그대로라서
`verify-deployment.sh`와 서버의 다른 서비스에 영향이 없다.

### 2. Cloudflare 터널 등록값

`infra/DEPLOY-ZORIN.md`와 `infra/scripts/set-tunnel-token.sh`의
Public Hostname URL:

| 이전 | 이후 |
|---|---|
| `web:80` | `web:8080` |
| `hcm-api:4080` | `api:4080` |
| `hcm-admin:3111` | `admin:3000` |

**뒤의 두 개는 별도의 결함이었다.** Compose에 `container_name`을
지정하지 않았으므로 컨테이너 이름은 `hotel-chain-manager-api-1` 같은
형태가 되지만, Compose 네트워크 안에서 DNS로 풀리는 이름은 **서비스
이름**이다. `hcm-api`·`hcm-admin`은 풀리지 않아 **터널이 502**를
냈을 것이다. `set-tunnel-token.sh`는 더 심했다 — `hcm-admin:3111`은
**호스트 포트**까지 적혀 있었다. 터널은 컨테이너 포트를 써야 한다.

### 3. `infra/PORTS.md` 추가

포트 할당을 한 곳에 모은 문서를 만들었다.

- **로컬 개발** (`compose.yaml`): `55432`·`55433`·`4080`·`9000`·
  `59090`·`4000`·`3000`. 호스트 포트를 의도적으로 연다.
- **Zorin 배포** (`compose.zorin.yml`): `3201`·`3110`·`3111`. 전부
  `127.0.0.1`에만 바인딩.
- **포트 대역 규칙**: `3100`~`3104`·`3200`은 같은 서버에서 이미 실행
  중인 다른 프로젝트(`b2b-stm`·`sdtpl-adm`·`real-es`·`music-pie`·
  `alpha-momega`)가 쓴다. 이 프로젝트는 `3110`·`3111`·`3201`.
- **80번 포트를 쓰지 않는 이유**와 **컨테이너 포트 vs 호스트 포트**를
  적었다. 터널 URL은 컨테이너 포트, `verify-deployment.sh`는 호스트
  포트를 쓴다는 것을 분리했다.
- **Cloudflare Public Hostname 등록표**와 **검증 표**를 넣었다.

`DEPLOY-ZORIN.md`의 서비스·포트 단락은 `PORTS.md`를 가리키게
요약하고, 중복 단락을 제거했다.

## 검증 결과

- **nginx 설정**: 실제 `nginx:1.29-alpine` 이미지에 프로젝트의
  `nginx.conf`를 주입하고 `nginx -t`를 실행했다. `syntax is ok`·
  `test is successful`. `${API_PROXY_TARGET}` 환경변수 치환도
  통과했다 (`API_PROXY_TARGET=http://api:4080`).
- **8080 수신**: nginx 컨테이너를 `127.0.0.1:18080:8080`로 띄워
  `http://127.0.0.1:18080/`에 접근했다. **STATUS=200**, 본문
  `port-8080-ok`. nginx 로그에 worker 프로세스가 정상 기동했다.
- **설정 일관성**: `nginx.conf`(`listen 8080`)·`Dockerfile`
  (`EXPOSE 8080`)·`compose.zorin.yml`(`3110:8080`, 헬스체크
  `8080`)·`DEPLOY-ZORIN.md`·`set-tunnel-token.sh`·`PORTS.md`의
  8080·8080·3110·8080 값이 전부 일치한다. `grep`으로 확인했다.
- **`verify-deployment.sh`**: 호스트 포트(`3110`·`3111`·`3201`)를
  쓰므로 **변경이 없다.** 컨테이너 포트를 바꿔도 그대로 동작한다.

## 미검증 항목

- **서버에서 `docker compose up`을 실행하지 않았다.** 컨테이너
  빌드도 돌지 않았다. `nginx.conf` 단독으로 검증했을 뿐, 전체
  빌드 파이프라인에서 `EXPOSE 8080`과 매핑이 함께 동작하는지는
  서버에서 기동해야 알 수 있다.
- **Cloudflare 대시보드의 Public Hostname을 직접 등록하지 않았다.**
  이 값들은 대시보드에 수동으로 입력해야 한다. 사용자가
  `PORTS.md`의 표를 보고 등록한다.
- **터널 경유 검사(`verify-deployment.sh`의 뒤 3개)를 실행하지
  않았다.** 터널과 도메인이 서버에 없다.
- **로컬 개발 compose.yaml은 건드리지 않았다.** 로컬은 nginx를
  쓰지 않고 Vite 개발 서버(`4000`)를 직접 쓴다.

   한다.**

   경유 도메인을 검사한다. 앞의 3개(로컬)가 통과하는데 뒤의
   3개(터널)가 실패하면 Cloudflare의 URL 값을 확인한다.
