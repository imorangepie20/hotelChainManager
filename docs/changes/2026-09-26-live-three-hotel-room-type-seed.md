# 라이브 3개 호텔 객실유형·요금·재고 시드 적용

> 날짜: 2026-09-26

## 문제

관리자 `객실유형` 화면은 서버의 호텔 목록에서 첫 호텔을 자동 선택하지만,
`재고·가격` 화면은 속초 호텔을 기본 선택하고 있었다. 라이브 DB에는 속초 호텔만
객실유형 3개와 요금·재고 시드가 있었고 설악·제주 호텔은 객실유형이 0개였다.
그 결과 두 화면이 서로 다른 호텔을 가리킬 때 객실유형은 비어 있고 재고·가격에는
데이터가 있는 것처럼 보였다.

로컬 `R__demo_data.sql`에는 이미 3개 호텔 전체 시드가 있었지만, 앞선 터널 배포는
인프라 관련 파일만 선별 반영했기 때문에 이 시드 파일은 라이브 서버에 올라가지
않았다.

## 조치

- 적용 전 원격 시드 파일과 PostgreSQL 전체 덤프를
  `backup/pre-three-hotel-seed-20260926-180701`에 보관했다.
- `services/api/src/main/resources/db/dev/R__demo_data.sql`만 원격 서버에 반영했다.
- API 이미지를 다시 빌드하고 API 컨테이너만 재생성했다.
- Flyway가 repeatable migration `demo data` 1건을 적용했다.
- 시드는 `ON CONFLICT DO NOTHING` 방식이라 기존 속초 호텔의 객실유형·요금·재고를
  덮어쓰지 않고 설악·제주에 빠진 행만 추가했다.

## 검증

- PostgreSQL 호텔별 집계
  - 속초: 객실유형 3, 요금제 3, 재고 일자행 273, 가격 일자행 273
  - 설악: 객실유형 3, 요금제 3, 재고 일자행 270, 가격 일자행 270
  - 제주: 객실유형 3, 요금제 3, 재고 일자행 270, 가격 일자행 270
- 실제 HQ 직원 세션으로 `GET /api/staff/hotels/{hotelId}/room-types`를 호출해
  세 호텔 모두 `totalCount=3`을 확인했다. 비밀번호와 세션 토큰은 출력하지 않았다.
- `infra/scripts/verify-deployment.sh` 전체 통과
  - API·고객 웹·관리자 웹 컨테이너 내부 점검 통과
  - `hcm.approid.team` API·웹과 `admin-hcm.approid.team` 터널 경유 점검 통과

## 미검증·운영 참고

- 실제 브라우저 화면은 자동 조작하지 않았다. 이미 열린 관리자 화면에서는 새로고침한
  뒤 호텔을 다시 선택해야 최신 목록을 볼 수 있다.
- 속초의 273개 일자행은 기존 repeatable 시드 실행 이력이 남은 상태에서 새 날짜 구간을
  보충한 결과다. 기존 행은 삭제하거나 덮어쓰지 않았다.
