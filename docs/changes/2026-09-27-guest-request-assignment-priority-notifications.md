# 고객 요청 담당자·우선순위·유형별 알림

## 변경 이유

고객 요청 API는 담당자와 우선순위 변경 계약을 이미 갖고 있었지만 관리자 화면에서는 상태만 바꿀 수
있었다. 요청 유형별 담당 업무도 한눈에 구분되지 않았고, 지점 직원이 지정할 수 있는 담당자 범위를
서버에서 행위자 기준으로 제한하지 않았다. 본사는 전체 지점, 지점 직원은 자기 지점만 처리한다는
원칙을 조회·후보 목록·변경·알림에 동일하게 적용했다.

## 구현 내용

- `GET /api/staff/guest-requests/{requestId}/assignees`가 요청 접근 권한을 먼저 확인한 뒤 지정 가능한
  활성 직원의 ID·표시명·역할·지점만 반환한다. 본사 관리자는 본사 관리자와 요청 지점 직원을,
  지점 직원은 자기 지점의 지점 직원만 지정할 수 있다. 변경 명령도 같은 정책을 다시 검증한다.
- `GET /api/staff/guest-requests/notifications`가 최근 `OPEN` 요청을 유형별 앱 내 알림으로 계산한다.
  고객 이름·연락처·제목·본문·처리 메모는 응답에 넣지 않고 최대 20건만 반환한다. 별도 발송 행이
  없으므로 외부 알림 중복이나 재시도 부작용이 없다.
- 접수 멱등 키를 `guest_request_submission_command`에서 독립적으로 선점한다. 같은 키·같은 본문은
  기존 요청을 재생하고 같은 키·다른 본문은 409로 거부한다. 요청 지문 advisory lock으로 같은 내용의
  동시 재시도를 한 요청으로 모은다. 기존 요청 행은 보존한다.
- V69가 요청 지문 조회와 본사 전체 `OPEN` 최신순 알림 조회 인덱스를 추가한다.
- 모든 고객 요청 성공 응답과 로컬 404·409 응답은 `Cache-Control: no-store`를 사용한다. 처리 안내는
  서버에서도 500자로 제한한다.
- 관리자 목록·상세에 한국어 우선순위를 표시하고 유형별 알림 요약과 `담당·우선순위 변경`
  대화상자를 추가했다. 후보 조회 완료 후 담당자 select로 초점을 옮기고 닫을 때 실행 버튼으로
  복귀하며 390px에서 대화상자를 문서 폭 안에 유지한다.
- 담당자·우선순위 변경은 기존 transition 명령과 append-only `ASSIGNED`·`PRIORITY_CHANGED` 감사
  이벤트를 재사용한다. 상태를 유지한 변경도 감사 화면에 반영된다.

## 검증 결과

- `GuestRequestIntegrationTest`: 39건 통과. 유형별 알림 매핑, 개인정보 비노출, 본사/지점 범위,
  처리 후 알림 제거, 후보 범위, 지점 직원의 본사 담당자 지정 차단, 접수 재시도·멱등 키 충돌,
  500자 초과 처리 안내 롤백과 인증 실패 응답의 캐시 금지를 확인했다.
- `AuditIntegrationTest`: 20건 통과. 담당자·우선순위 변경의 기존 감사 통합과 마스킹 회귀를 확인했다.
- 관리자 `guest-requests.spec.ts`: Chromium 9건 통과. 알림 요약, 목록·상세 우선순위, 변경 payload,
  감사 이벤트 표시, 키보드 열기·닫기·초점 복귀와 390×844 가로 넘침 방지를 확인했다.
- TypeScript 검사, 변경 파일 ESLint(오류 0, 기존 effect 경고 3), production build가 통과했다.
