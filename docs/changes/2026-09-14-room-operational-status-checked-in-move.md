# 실제 객실 점검·판매 중지와 투숙 중 객실 이동

## 구현 범위

- `physical_room`의 청소 상태와 운영 상태를 분리해 `AVAILABLE`, `INSPECTION_REQUIRED`, `OUT_OF_SERVICE`를 관리한다. 운영 상태에는 사유, 예상 복구 시각, 낙관적 잠금 version과 변경 시각을 저장한다.
- 당일 운영 화면에 지점별 객실 운영 요약·필터·상태 전환 대화상자·영향 예약 링크를 추가했다. 판매 중지는 투숙 중 또는 미래 확정 배정이 있으면 409로 거부하고 최신 영향 목록을 표시한다.
- 체크인 중인 예약 상세에서 같은 호텔·객실 유형의 `CLEAN + AVAILABLE` 미점유 객실로 한 실씩 이동한다. 성공 시 이전 객실은 `NEEDS_CLEANING + INSPECTION_REQUIRED`가 되고 이동·운영 감사가 한 트랜잭션에 기록된다.
- 기존 신규 배정, 체크인 전 재배정과 체크인은 운영 불가 객실을 후보와 실행 단계 모두에서 제외한다. 객실 유형별 일자 재고는 실제 객실 번호와 계속 분리한다.
- V36은 운영 상태와 감사 기반을 추가하고 legacy 청소 상태의 판매 중지를 보수적으로 이관한다. V37은 지연된 멱등 재시도도 최초 응답을 그대로 재생하도록 결과 version·청소 상태 snapshot을 운영 이벤트에 추가한다.

## 상태·권한 정책

- 가격·재고·배정·체크인·상태 전환·투숙 중 이동의 최종 판단은 Spring Boot가 가진다. 본사 관리자는 모든 지점, 지점 직원은 소속 지점만 조회·변경할 수 있다.
- `OUT_OF_SERVICE` 전환은 현재 투숙 또는 아직 끝나지 않은 확정 배정이 있으면 차단한다. `AVAILABLE` 복구는 청소 완료 객실에서만 가능하며 자동 복구는 하지 않는다.
- 상태 전환과 투숙 중 이동은 직원까지 포함한 요청 지문과 `Idempotency-Key`를 사용한다. version 충돌이나 후보 선점 충돌 뒤 UI는 서버의 최신 상태·후보를 다시 읽고 새 요청 키를 사용한다.
- 실제 브라우저 검증은 읽기 전용으로 진행했으며 개발 예약, 객실 상태, 체크인·체크아웃을 변경하지 않았다.

## 검증 결과

- 백엔드 직접·인접 회귀 8개 클래스 64건: 실패 0, 오류 0, 건너뜀 0. 상태 전환, 지연 멱등 재생, 다실 예약 자기 대상 충돌, 이동 원자성·rollback·동시 선점, 기존 배정·재배정·예약 변경·취소 회귀를 포함한다.
- 전체 백엔드 suite는 기존 `WebsiteMediaVariantSchedulingTest` 1건이 `WebsiteMediaStorageGateway` bean 부재로 application context를 시작하지 못해 완료하지 못했다. 동일 테스트를 기능 변경 전 `main`에서도 단독 실행해 같은 실패를 재현했으므로 이번 변경과 무관한 선행 장애로 분리했다.
- 관리자 변경 파일 ESLint는 오류 0이며 기존 `daily-operations.tsx`의 `react-hooks/set-state-in-effect` 경고 2건이 남는다. `pnpm exec tsc --noEmit`과 Next.js 16.2.7 production build(정적 104개 route)는 통과했다.
- 기존 관리자 4001을 재사용한 Chromium 회귀 4개 파일 13건이 통과했다. 390×844 대화상자, 키보드 포커스 복귀, 영향 예약 차단·딥링크, 응답 유실 재시도, 409 후 최신 상태·후보 재조회, 이동 후 권위 재조회를 포함한다.
- Compose API만 재빌드했고 4080 readiness는 200이다. 개발 DB `flyway_schema_history`에서 V36·V37 `success=true`를 확인했으며 관리자 4001도 계속 200이었다.
- 실제 인앱 브라우저의 `/dashboard/operations`에서 당일 운영 제목, 객실 운영 상태 영역, 점검 필요·판매 중지·예상 복구 지연 요약과 도착 예정·출발 예정·청소 필요 객실 카드를 확인했다. 1440px·390px 캡처의 finish review는 객실 목록 계층을 구분선 행으로 보완한 뒤 `ship` 판정을 받았다.

## 미검증·후속 범위

- 다른 객실 유형으로 이동하는 업그레이드·다운그레이드와 가격·결제 정산, 여러 객실 일괄 이동, 자동 객실 재배정은 포함하지 않았다.
- 실제 운영 다중 직원 장기 부하, 운영 배포 환경의 migration·모니터링, 실제 사용자 예약으로 상태 전환·투숙 중 이동하는 파괴적 브라우저 검증은 수행하지 않았다.
- 선행 전체-suite 장애인 `WebsiteMediaVariantSchedulingTest`의 test slice bean 구성을 별도 수정해야 전체 백엔드 suite를 다시 닫을 수 있다.

## 배포·롤백

- API와 V36·V37을 먼저 배포한 뒤 관리자 UI를 배포한다. migration은 새 운영 컬럼·감사 테이블·응답 snapshot 컬럼을 남기는 forward-only 방식이다.
- 이전 API로 일시 롤백할 때도 새 컬럼과 감사 데이터는 삭제하지 않는다. 이전 API는 새 운영 상태를 배정 조건에 반영하지 않으므로 신규 배정·재배정·체크인을 제한하고 장기간 운영하지 않는다.
- 복구 후 `physical_room_operational_event`와 `checked_in_room_move` 감사를 기준으로 현재 배정·운영 상태를 재확인한다. 스키마 자체를 되돌려야 하면 DB 백업 복원이 필요하다.
