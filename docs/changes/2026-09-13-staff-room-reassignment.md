# 체크인 전 배정 객실 변경

## 변경 이유

직원이 확정 예약의 객실 준비 상황이 바뀌었을 때 예약 조건을 건드리지 않고 배정된 실제 객실 한 실만 안전하게 교체할 수 있어야 한다.

## 구현 범위

- `CONFIRMED` 예약에서 현재 배정 객실 한 실을 같은 호텔·같은 객실 유형의 청결 객실 한 실로 변경한다.
- 후보 조회와 최종 변경 모두 직원 세션 및 지점 권한을 확인한다.
- 예약과 두 객실을 잠근 뒤 숙박 기간 충돌과 현재 배정 상태를 다시 검증한다.
- `Idempotency-Key`로 동일 요청 재시도를 보장하고 담당 직원, 이전·신규 객실을 감사 이력에 남긴다.
- 예약 상세에서 현재 객실과 신규 객실을 각각 선택해 한 실씩 변경한다.

## 완료 기준

- 변경 성공 후 기존 배정은 제거되고 신규 배정만 남는다.
- 청소가 필요한 객실, 타 지점·타 유형 객실, 겹치는 예약에 사용 중인 객실은 변경할 수 없다.
- 체크인 이후 상태에서는 신규 변경을 거부하되 완료된 동일 요청 재시도는 같은 결과를 반환한다.
- 동일 키에 다른 직원이나 다른 객실 변경 요청을 보내면 충돌로 처리한다.
- 오류 후 같은 선택으로 재시도할 수 있고 성공 시 예약 목록이 갱신된다.

## 제외 범위

- 체크인 이후 객실 재배정과 객실 배정 해제
- 날짜·객실 유형·요금제·인원·가격·결제 변경
- 여러 객실 일괄 변경 및 자동 후보 추천

## 호환성과 롤백

- 기존 예약·객실 배정 테이블은 변경하지 않고 감사 테이블만 추가한다.
- API와 UI를 되돌려도 기존 배정 기능은 유지된다. 감사 테이블은 운영 기록 보존을 위해 남기며 제거가 필요하면 별도 하향 migration으로 처리한다.

## 검증 결과

- `StaffRoomReassignmentIntegrationTest` 8건과 기존 `StaffOperationsIntegrationTest` 14건, 합계 22건이 통과했다. 성공·감사 상세, 상태 변경 뒤 멱등 재시도, 동일 키의 다른 객실·직원 충돌, 청소 필요·겹치는 예약·타 유형·타 지점·미배정 현재 객실 거부, 두 예약의 동일 후보 동시 요청에서 한 건만 성공하는 것과 HTTP 계약을 확인했다.
- 예약 관리 Chromium E2E 4건이 통과했다. 모바일에서 후보 선택, 오류 표시, 선택 변경 시 요청 키 교체, 동일 선택 재시도 시 키 유지, 성공 뒤 목록 갱신과 기존 조회·예약자 정정·추가 배정 흐름을 확인했다.
- 변경 프런트 파일 ESLint와 UI detector가 통과했다.
- Next.js production build가 `/dashboard/reservations`를 포함한 정적 페이지 104개를 생성했다.
- 로컬 API 컨테이너를 재빌드해 Flyway V31 적용, API 4080과 관리자 4001의 HTTP 200 응답을 확인했다.
- 체크인 이후 실제 객실 이동, 여러 서버 인스턴스 간 부하 테스트와 운영 데이터 규모의 성능 측정은 제외 범위이므로 검증하지 않았다.
