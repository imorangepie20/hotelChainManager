# 토스 결제창 실패 진단

## 최종 상태

- 위젯 키 결제창, 340,000원 실제 테스트 승인, 서버 예약 확정과 사용자 결과 화면을 확인했다. 이어 직원 API 취소·토스 전액 환불 한 건·잔액 0원·양일 재고 반환을 확인했다.
- 결제 실패 단계와 안전한 오류 안내를 추가하고, 만료된 예약의 재승인을 차단했다. 위젯 SDK 4건·결제/진단/복구 직접 테스트와 TypeScript 검사 통과.
- 추가 결제·부분 환불·고객 취소 UI 클릭·외부 webhook 전달은 미검증이다. 아래 조사 기록의 미검증 표기는 각 조사 시점의 상태다.

## 실제 테스트 취소·환불 검증 계획

- 확정된 340,000원 테스트 예약 한 건을 대상으로 취소 미리보기·취소 요청·토스 인증 조회·DB 환불 원장·숙박일별 재고를 대조한다.
- 브라우저 제어 연결이 시간 초과되어 개발 직원 계정의 정상 로그인과 취소 API를 이용한다. 고객 UI 클릭 검증과 구분한다.
- 취소 전 9월 21일·22일 재고는 held=0, confirmed=1이다. 완료 기준은 토스 CANCELED, 340,000원 환불 한 건, 예약 CANCELLED 및 각 숙박일 confirmed=0이다. DB 상태를 직접 수정하지 않는다.

## 실제 테스트 취소·환불 검증 결과

- 개발 속초 직원 계정으로 정상 로그인해 취소 가능·340,000 KRW 전액 환불 미리보기를 확인했다. 취소 API는 CANCELLATION_PENDING을 반환했고 사용한 직원 세션은 로그아웃했다.
- 비동기 환불 처리 후 DB에서 예약 CANCELLED, 환불 명령 SUCCEEDED, 누적 환불액 340,000원을 확인했다. 9월 21일·22일 모두 held=0, confirmed=0으로 재고가 반환됐다.
- 토스 인증 조회에서도 CANCELED, 잔액 0원, DONE 취소 이벤트 1건·340,000원을 확인했다.
- 고객 브라우저 제어는 연결 시간 초과로 검증하지 못했다. 실제 과금 없는 테스트 거래만 사용했고 DB 상태 직접 수정이나 별도 토스 취소 호출 없이 애플리케이션 취소 경로를 통과했다.

## 상점 ID 불일치 복구 계획

- 새 테스트 예약의 주문은 UNKNOWN이지만 설정된 시크릿 키로 인증한 토스 조회는 DONE, 340,000 KRW를 반환했다. 저장 결제 키가 일치하고 응답 mId와 로컬 상점 설정이 다르다.
- 응답 주문·결제 키·금액·통화를 저장 주문과 모두 대조한 뒤 Git 제외 상점 설정과 해당 UNKNOWN 주문의 상점 메타데이터만 교정한다. 예약·결제 상태나 재고는 SQL로 확정하지 않는다.
- API만 설정을 재적용하고 기존 webhook 조회 큐로 토스 재조회를 요청한다. 완료 기준은 서버 처리로 CONFIRMED/SUCCEEDED, 원 결제 거래 한 건 생성이다. 신규 승인 요청은 보내지 않는다.

## 상점 ID 불일치 복구 결과

- 인증된 토스 조회의 주문·결제 키·340,000 KRW·DONE 상태를 저장 주문과 대조한 뒤 실제 mId로 `.env`와 해당 UNKNOWN 주문 한 건의 상점 메타데이터를 교정했다. 키 값과 상점 ID 원문은 기록하지 않았다.
- API 컨테이너만 재생성하고 readiness UP을 확인했다. 기존 webhook endpoint에 저장 주문의 조회 힌트를 넣어 HTTP 202를 받았고, 서버의 인증 재조회로 예약 CONFIRMED·결제 SUCCEEDED·ORIGINAL_CHARGE 1건·340,000원을 확인했다.
- 예약 상태·결제 상태·재고를 직접 수정하거나 재승인하지 않았다. 고객·관리자 서버는 재시작하지 않았다.
- `.env.example`에 상점 설정은 임의 이름이 아니라 실제 MID임을 명시했다. 실제 테스트 승인과 서버 예약 확정은 확인됐으며 환불·변경 추가 결제·외부 webhook 전달은 미검증이다. 사용자 결과 화면은 재확인 버튼으로 최신 상태를 읽을 수 있다.

## 계획과 완료 기준

- 결제창 실패를 한 문구로 숨기는 문제를 수정한다. 주문 생성 API, 결제 설정 검증, SDK 로딩, 결제창 호출 단계를 구분한다.
- 원문 오류·키·예약 토큰은 표시하거나 로그에 남기지 않는다. 알려진 오류 코드를 한국어 안내로 변환한다.
- 직접 테스트로 단계 구분과 비밀값 비노출을 검증하고 고객 TypeScript만 검사한다.
- 브라우저 제어 시간 초과로 실제 Chrome 결제창 성공 여부는 미확인이다. 인앱 브라우저의 SDK 주소 차단만 확인됐으며, 기존 예약의 현재 만료 상태는 최초 실패 원인의 증거가 아니다.

## 결과

- 신규 예약 결제 버튼에 API / CONFIG / SDK / PAYMENT_WINDOW 단계별 안내와 알려진 오류 코드 안내를 적용했다.
- Toss 클라이언트 직접 테스트, 진단 메시지 4건, 고객 TypeScript 검사와 diff 검사를 통과했다.
- 원문 오류는 표시하지 않는다. 미등록 코드에 비밀값을 넣은 테스트도 고정 안내만 반환했다.
- 다음 작업: Chrome 결제 버튼에서 표시되는 실패 단계·코드로 실제 결제창 실패를 확정한다. 실제 승인·환불 성공은 아직 검증되지 않았다.

## 키 종류 불일치 확인

아래 개별 키 교체 안내는 철회한다. 사용자가 해당 키를 발급받을 수 없으므로 기존 위젯 키를 지원하는 공식 결제창형 SDK로 연결한다.

- 사용자 Chrome 캡처에서 checkout HTTP 200, SDK 실행 후 PAYMENT_WINDOW 오류를 확인했다.
- 값 노출 없이 `.env`의 키 종류를 확인한 결과 test_gck_/test_gsk_였다. 현재 사용하는 payment()는 API 개별 연동 키를 요구하며 공식 SDK 소스에서도 위젯 키 거절 분기를 확인했다.
- 위젯용 키를 SDK 호출 전에 판별하고 NOT_SUPPORTED_WIDGET_KEY 안내를 표시한다. 개발자센터에서 결제창(구버전)용 test_ck_/test_sk_ 한 쌍으로 교체해야 한다. 기존 사용자 키는 임의로 변경하지 않았다.
- 참고: https://docs.tosspayments.com/reference/using-api/api-keys 및 https://docs.tosspayments.com/sdk/v2/js/payment

## 위젯 키 지원 계획

- test_gck_는 widgets → setAmount → renderPaymentWindow → paymentRequest 이벤트 → requestPayment로 연결한다. test_ck_의 기존 경로는 유지한다.
- 서버 주문·금액·복귀 주소만 사용하고 창 종료 또는 요청 실패 시 destroy로 해제한다. 이벤트 중복 요청을 막는다.
- 직접 SDK 계약 테스트로 금액 설정 순서, 결제 이벤트 전 미요청, 취소 후 재시도, 요청 실패 정리, 기존 경로를 검증한다. 실제 PG 승인 성공과는 구분한다.
- 공식 계약: https://docs.tosspayments.com/sdk/v2/js/payment-window

## 위젯 키 지원 결과

- 신규 예약과 변경 추가 결제의 공통 SDK 함수에 위젯 키용 결제창형 경로를 반영했다. .env 키와 백엔드는 변경하지 않았다.
- 직접 SDK 계약 테스트 4건, 기존 클라이언트·진단 테스트, 고객 TypeScript 검사와 diff 검사가 통과했다.
- 사용자 Chrome 캡처로 테스트 결제창 표시를 확인했다. PG 승인·환불은 미검증이다.

## 결제 결과 확인 실패 조사·수정 계획

- 결과 화면의 예약 ID와 DB를 대조했다. 해당 예약은 EXPIRED이며 결제 주문은 NEW, 결제 키가 저장되기 전이다. 현재 상태만으로 최초 승인 요청의 오류 원인을 단정하지 않는다.
- 결과 화면은 모든 API 오류를 같은 문구로 숨긴다. 알려진 오류 코드와 HTTP 상태만 표시하고 원문·비밀값은 노출하지 않는다.
- 재조회가 EXPIRED/NEW를 반환해도 다시 승인을 요청하는 문제를 직접 테스트로 재현한다. PENDING_PAYMENT/NEW에서만 기존 callback으로 복구하고 만료 상태를 명확히 안내한다.
- 완료 기준: 직접 복구·진단 테스트, TypeScript 검사, 현재 결과 화면에서 재조회 안내 확인. 실제 승인 성공은 별도로 검증한다.

## 결과 확인 오류 수정 결과

- EXPIRED/NEW 상태에서 재승인하는 동작과 만료 상태를 확인 중으로 표시하는 동작을 실패 테스트로 재현한 뒤 수정했다. APPROVING/UNKNOWN은 새 결제를 권하지 않고 기존 조회 안내를 유지한다.
- 복구·결제 메시지·진단 직접 테스트 및 TypeScript, diff 검사를 통과했다. 결과 화면에는 CONFIRM/STATUS 단계, 알려진 오류 코드 또는 HTTP 상태만 표시한다.
- 실제 해당 예약의 DB는 EXPIRED/NEW, payment_key 없음, 결제 거래 0건이다. 브라우저 예약 화면에서도 같은 예약의 만료 안내를 확인했다.
- 결과 화면으로의 자동 이동은 시간 초과되어 수정된 결과 UI와 실제 승인 성공은 미검증이다. 최초 HTTP 오류 응답은 확보하지 못했다. 다음 검증은 새 확보 예약의 10분 이내 테스트 결제이며, 실패 시 화면의 단계·오류 코드로 이어서 조사한다.
