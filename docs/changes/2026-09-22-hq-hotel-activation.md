# 본사 지점 관리 - 지점 판매 중지·재개 (2026-09-22)

> 상태: 작업 트리에만 있고 커밋하지 않은 상태.

## 변경 이유

`admin-menu-roadmap.md` 1번 `지점·객실 유형 관리`의 남은 항목 중 "지점 판매 중지"를 구현했다. **본사가 리모델 공사나 브랜드 정비로 한 지점의 예약 접수를 멈출 수단이 없었다.** `hotel` 표에 판매 상태 칼럼이 없었으므로 점검 기간인 지점도 고객 `GET /api/hotels`·`GET /api/availability`에 계속 나타나서 고객이 예약을 시도하게 됐다. 재고를 0으로 내리는 임시 방편은 가능하지만 **재고 0은 "매진"이지 "판매하지 않는다"가 아니므로** 본사가 의도를 가지고 중지·재개할 수 있는 상태가 필요했다. [설계서](../plans/2026-09-22-hq-hotel-activation.md)를 먼저 기록했다.

## 서버 변경

- `PATCH /api/staff/hotels/{hotelId}/active`가 지점의 판매를 중지·재개한다. `HQ_ADMIN`만 허용하고 지점 직원은 403, 잘못된 세션은 401, 멱원 키 누락은 400, `active` 필드 누락은 400, 없는 지점은 404다.
- **중지는 고객 `GET /api/hotels`·`GET /api/availability`에서 지점을 빼는 것이다.** `HotelController.list()`가 `where active`로 걸러주고, `AvailabilityService`가 `active`가 아닌 지점에 빈 오퍼를 내려준다. 예약할 수 없다는 것이지 오류가 아니다.
- **이미 확정된 예약은 그대로 둔다.** 중지가 예약을 취소하면 본사가 고객에게 알리지 않은 채 환불 의무가 생기므로, 중지는 신규 판매에만 적용한다. 취소는 전용 API가 있다.
- **직원은 중지한 지점도 본다.** `HotelQueryService.list()`가 `order by active desc, name`으로 내려준다. 다시 판매하려면 상태를 알아야 하므로 고객 화면과 다르다.
- **중지한 지점의 객실 유형에 본사가 여전히 요금·재고를 바꿀 수 있다.** 본사는 점검 기간에도 가격·재고를 정비해야 하므로, 중지가 쓰기 권한에 영향을 주지 않는다.
- **판매 재개는 재고를 다시 심지 않는다.** 중지는 `inventory_day`·`rate_day`를 건드리지 않으므로 재개하면 중지 전과 같은 재고가 돌아온다.
- 멱원은 두 갈래로 동작한다. 같은 `Idempotency-Key` 재호출은 200에 `changed=false`로 같은 결과를 돌려주고, 응답 유실 뒤 새 키로 같은 내용을 보내도 `staff_id`·지점·`active`의 SHA-256 지문이 같아 같은 결과를 돌려준다.
- **이미 같은 상태면 DB를 건드리지 않고 멱원 기록만 남긴다.** 재시도가 200으로 같은 결과를 돌려주게 한다. `changed` 필드로 값이 바뀌었는지 알려준다.
- 지점 행을 `select ... for update`로 잡아 두 본사 관리자가 같은 지점을 동시에 바꾸면 한 쪽이 기다리도록 직렬화한다.

## 마이그레이션 변경

- V60 additive 마이그레이션이 `hotel.active BOOLEAN NOT NULL DEFAULT TRUE`를 추가한다. **기존 3개 지점은 모두 활성이므로 기존 동작을 변경하지 않는다.**
- `hotel_command` 표를 재사용한다. V59가 이미 `kind`(`CREATE`·`UPDATE`) 칼럼을 가지고 있어 `ACTIVATE`를 추가했다. **V59·V60 모두 아직 커밋되지 않은 상태**이므로 제자리에서 다듬었다. 라이브 DB에는 영향이 없다.

## 관리자 UI 변경

- `호텔 및 객실` (`/dashboard/hotels`)의 지점 표에 `판매` 열을 추가했다. `Badge`가 `판매 중`·`판매 중지`를 보여준다.
- 지점 행의 `판매 중지`·`판매 재개` 버튼이 `PATCH /api/staff/hotels/{hotelId}/active`를 부른다. **중지·재개는 매번 새 멱원 키를 쓴다.** 재시도가 같은 키를 재사용하지 않게 해서 네트워크 장애 뒤 다시 눌러도 중복 전환이 생기지 않는다.
- 실패 안내는 표 위에 남기고 상태는 바꾸지 않는다. 서버 검증 실패 시 `Badge`가 그대로다.
- `staff-api.ts`의 `setHotelActive`를 추가했다. `UpdatedHotel` 타입을 재사용한다.

## 검증 결과

- API `mvnw -Dtest=HotelActivationIntegrationTest` **14건**이 종료 코드 0이다. 중지 200 `changed=true`·재개 200 `changed=true`·고객 지점 목록에서 빠짐·빈 오퍼·같은 키 재호출 200 `changed=false`·새 키 같은 내용 200 `changed=false`·같은 상태 no-op 200 `changed=false`·확정 예약 보존·지점 직원 403·세션 없음 401·키 누락 400·`active` 필드 누락 400·없는 지점 404·직원 목록에 중지 지점 포함을 다룬다.
- 인접 9개 suite **193건**이 종료 코드 0다(객실 유형 27·재고 16·요금 20·고객 요청 22·감사 16·운영 통계 18·직원 계정 47·지점 생성 13·지점 수정 14). V60 additive 마이그레이션이 기존 영역에 영향을 주지 않음을 확인했다.
- 관리자 `tsc --noEmit`이 종료 코드 0이고, `eslint`는 경고 3건만 낸다(`react-hooks/set-state-in-effect`, 기존 컴포넌트와 같은 패턴).
- Playwright `hotel-catalog` **22건**(기존 20 + 신규 2)이 종료 코드 0이다. 새 검증은 중지→`판매 중지` 배지·버튼이 `판매 재개`로 바뀜, 403 안내가 표시되고 상태가 바뀌지 않음이다. 인접 6개 suite **68건**도 종료 코드 0이다.

## 발견·수정한 결함

1. `2026-09-22-hq-hotel-update.md`에서 "판매 중지는 별도 설계가 필요하다. `hotel` 표에 판매 중지 칼럼이 없다"고 남겨둔 미검증 항목을 이 작업이 해결했다. 중지가 진행 중인 예약을 건드리지 않는 조건을 명시하고 테스트로 확인했다.
2. **`HotelActivationIntegrationTest.stoppedHotelIsHiddenFromCustomers`가 중지 전후를 모두 검사하지 않으면 빠짐이 우연히 통과할 수 있다.** 중지 전에 지점이 고객 목록에 있는 것을 먼저 확인하고, 중지 뒤에 빠지는 것을 확인했다. `stoppedHotelReturnsNoOffers`도 같은 구조다.

## 미검증 항목

- **라이브 DB·compose 재빌드·브라우저 확인은 실행하지 않았다.** V60이 라이브에 적용되지 않았으므로 실제 중지 흐름은 사용자가 확인한다.
- **중지한 지점에서 진행 중인 예약 변경 요청·체크인·객실 배정이 여전히 동작한다.** 의도된 동작이지만(신규 판매만 막는다), 본사가 "판매 중지 = 운영 중지"로 오해할 수 있다. UI 안내에 "신규 판매만 막는다"를 적었다.
- **고객 웹사이트의 CMS 페이지는 중지한 지점을 가리키는 링크가 그대로 남는다.** `website_page`·`website_page_room_type`이 `hotel.active`를 보지 않는다. CMS에서 수동으로 정리해야 한다.
- **중지한 지점의 기존 페이지를 예약 화면에서 숨기지 않는다.** AI 예약 컨시어지의 `/chat` 컨텍스트도 `hotel.active`를 보지 않으므로 중지한 지점을 추천할 수 있다. AI는 조회 결과만 안내하므로 가격·재고를 생성하지는 않지만, 추천에서 빼야 하는지는 별도 결정이다.
- **감사 이력(7번 메뉴)에 판매 중지가 기록되지 않는다.** `hotel_command`는 멱원용 표이지 감사 표가 아니다. V29~V37 감사 표와 통합할 때 다룬다.
- **두 본사 관리자가 같은 지점을 반대 방향으로 동시에 바꾸면 마지막 쓰기가 이긴다.** `for update`가 직렬화할 뿐 방향을 판단하지 않는다. 마지막 상태가 멱원 기록과 일치하므로 데이터는 일관된다.
