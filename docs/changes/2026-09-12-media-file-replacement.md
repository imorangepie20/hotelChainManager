# CMS 미디어 파일 교체

## 변경 이유와 승인 범위

기존 미디어 선택·업로드는 새 이미지를 적용할 수 있지만 파일 교체의 범위와 공개 영향을 따로 안내하지 않았다. 리조트 CMS 설계의 불변 파일 정책에 맞춰 새 자산을 생성하고 현재 편집 위치만 명시적으로 교체한다. 사용자는 기존 파일·다른 페이지·발행 이력을 보존하고 초안 저장 후 발행해야 공개되는 범위를 승인했다.

## 구현

- 공통 `MediaField`에 `파일 교체`를 추가했다. 기존 관리자 테마·미디어 선택기·AlertDialog를 재사용한다.
- 기존 본사 업로드 API로 새 UUID·storage key·전달 URL을 만든다. 파일 덮어쓰기·신규 mutation API·DB migration은 추가하지 않았다.
- 이번에 업로드한 활성 자산만 교체 후보로 확정할 수 있다. 기존·새 이미지와 페이지별 alt를 표시한 확인창에서 `교체하기`를 눌러야 적용한다.
- 지점 대표 이미지, 홈·일반 페이지 HERO, 갤러리 항목에 같은 흐름을 제공한다. 현재 위치의 alt는 유지하고 일반 `미디어 선택`은 기존처럼 기본 alt를 복사한다.
- 적용은 메모리 초안만 변경한다. 초안 저장·발행 버튼과 서버의 기존 version·미디어 검증·usage 동기화를 그대로 사용한다.
- 취소·업로드 오류·닫기 이후 도착한 업로드 응답은 현재 페이지를 변경하지 않는다. 재진입 시 이전 업로드 후보를 초기화한다.
- 업로드 뒤 취소한 새 자산은 카탈로그에 남는다. 기존 자산은 자동 보관·삭제하지 않는다.

## 검증

- TDD RED: 구현 전 교체 테스트가 `파일 교체` 버튼 부재로 실패했다.
- 관리자 Chromium 직접 E2E 13건 통과: 새 교체 7건과 기존 미디어 선택·업로드·오류·메타데이터·보관/복원·버전 충돌 회귀 6건.
- 새 교체 테스트는 확인 전 페이지 mutation 요청 부재, 업로드만 수행, 확인 후 현재 UUID/URL만 저장, alt 유지, 미저장 발행 차단, 취소·Escape·포커스 복귀·재진입 초기화, 잘못된 파일, 취소 뒤 지연 응답, 홈과 갤러리 다른 위치 보존을 확인한다.
- 데스크톱·390×844 모바일 확인창의 로딩 완료 이미지와 배치를 스크린샷으로 확인했다. 화면 fixture는 새 업로드의 전달 응답에 기존 로컬 PNG를 사용하며 실제 새 파일의 PNG/JPEG 바이트는 서버 통합에서 검증한다.
- `WebsiteMediaIntegrationTest` 15건 통과(실패·오류 0). 추가 보존 테스트는 실제 PNG/JPEG 업로드·새 UUID/URL·업로드 전후 페이지 불변·저장 후 공개본 유지·발행 후 공개 반영·초안/발행 usage·다른 페이지·과거 snapshot·기존 파일 바이트·기존 자산 version을 확인했다.
- 관리자 TypeScript `tsc --noEmit` 통과. 직접 ESLint는 오류 0, 경고 12건이다. 기존 effect/dependency 경고와 기존·새 미리보기의 일반 `img` 경고는 남는다.
- Maven wrapper는 로컬 `.m2` 경로 처리 오류로 시작하지 못해 설치된 동일 버전 Maven 3.9.16을 사용했다. 의존성 JAR 접근은 샌드박스에서 차단되어 승인된 권한으로 테스트를 실행했다. 추가 테스트 fixture의 필수 SEO 누락을 보완한 뒤 15건이 통과했다.
- 로컬 API `4080` health `UP`, 기존 `/brand/story` 공개 resolve `CONTENT_PAGE`를 읽기 전용으로 확인했다.

## 미검증 항목과 다음 작업

- 실제 사용자 페이지·자산에는 업로드·저장·발행·보관·삭제 요청을 보내지 않았다. 변경된 UI는 기존 관리자 개발 서버에서 fixture로 직접 상호작용했다.
- API production 코드·schema 변경이 없으므로 Docker API 재빌드는 하지 않았다. 전체 서버 테스트·전체 관리자 브라우저 회귀·고객 예약 결제 회귀·고객 웹 빌드는 이번 범위에서 실행하지 않았다.
- 자산의 모든 사용 위치 일괄 이동, variant·변환·CDN·객체 저장소는 후속 범위다.
