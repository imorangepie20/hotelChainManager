# 고객 웹 Playwright 기준선 복구와 카탈로그 쓰기 기능 감사

## 범위

- 원본 계획: [고객 웹 Playwright 기준선 복구와 카탈로그 쓰기 기능 감사 계획](../plans/2026-09-27-customer-playwright-baseline-and-catalog-write-audit.md)
- 고객 웹 전체 회귀에서 계속 실패하던 5건을 원인별로 분리했다.
- 관리자 로드맵 1번 `지점·객실 유형 관리`와 2번 `재고·가격 관리`의 쓰기 기능을 API·UI·테스트에 대조했다.

## RED

- 격리된 로컬 고객 웹에서 Playwright 전체 실행 결과는 `29 passed / 5 failed`였다.
- 4건은 현재 계약과 어긋난 테스트였다. 영문 예약의 필수 전화번호가 빠졌고, `dt`에 접근성 이름이 있다고 가정했으며, 예약 변경 폴링의 순간 상태를 경쟁 조건으로 검사했고, 클릭 뒤 문구가 바뀐 버튼을 이전 이름으로 다시 찾았다.
- 이 4건을 실제 사용자 계약에 맞게 결정적으로 고친 뒤 대상 실행은 `4 passed / 1 failed`였다.
- 남은 실제 결함은 `toss-test` 모드에서 서버가 `live_*` 클라이언트 키를 반환해도 외부 Toss SDK 요청이 1건 발생하는 것이었다. 단위 계약도 환경 불일치를 거부하지 않아 RED였다.
- RED 체크포인트: `d7b63e1 test: isolate customer payment regressions`.

## GREEN

- `validateTossCheckout`에 선택적 결제 provider 검사를 추가했다. `toss-test`는 `test_`, `toss-live`는 `live_` 키만 허용한다.
- 신규 예약과 예약 변경 결제 모두 현재 서버 결제 모드를 SDK 호출 함수에 전달한다. 불일치는 설정 단계에서 거부하므로 SDK 스크립트를 내려받지 않는다.
- GREEN 체크포인트: `e311d0b fix(web): validate Toss key environment before SDK load`.

## 호텔·객실 및 재고·가격 감사

- 로드맵 1번의 지점 생성·수정·판매 중지, 객실 유형 생성·수정·삭제, 요금제 생성·이름 변경과 로드맵 2번의 재고 조정, 일자별 요금, 판매 중지·재개, CSV 내보내기·업로드가 모두 관리자 API 함수와 UI 조작에 연결돼 있다.
- 관리자 Chromium 61건이 전부 통과했다. 본사 권한, 지점 전환 중 쓰기 잠금, 서버 오류 유지, 390px 재고 표를 포함한다.
- Spring 통합 테스트 12개 클래스 206건이 전부 통과했다. 권한·멱원·충돌·트랜잭션·공개 가용성 반영을 포함한다.
- 구현 누락이 발견되지 않아 중복 생산 코드는 추가하지 않았다.

## 커버리지와 미검증

- 이 저장소의 고객 웹에는 명령형 계약 테스트와 Playwright가 있으나 문장·분기 커버리지 수집 구성이 없다. 따라서 80% 수치 커버리지는 측정하지 않았고 통과했다고 주장하지 않는다.
- 운영 결제·예약·재고에는 변경 요청을 보내지 않았다. 브라우저 테스트는 로컬 서버와 가짜 API·SDK 응답만 사용했다.
- Maven Wrapper 3.3.4의 Windows `Target[0]` 처리 오류 때문에 기존 Maven 3.9.16 실행 파일과 사용자 로컬 저장소를 명시해 같은 테스트 목표를 실행했다.
