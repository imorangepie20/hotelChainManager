# 본사 재고·가격 - 판매 중지 구간 설정 (2026-09-24)

> 상태: 작업 트리에만 있고 커밋하지 않은 상태. 뒤이은 [재고 일괄 업로드](2026-09-24-hq-inventory-import.md)가 `salesStatus` 열을 재사용한다.

## 변경 이유

`admin-menu-roadmap.md` 2번 `재고·가격`의 남은 항목 중 "판매 중지 구간
설정"을 구현했다. 1번 영역(지점·객실 유형 관리)이 완료됐으므로 로드맵
순서(1 → 2 → 3 → 5 → 4 → 7 → 6 → 8)에 따라 2번의 남은 항목으로 넘어왔다.
[설계서](../plans/2026-09-24-hq-sales-status.md)를 먼저 기록했다.

본사가 특정 날짜의 판매를 멈추는 유일한 수단은 `PATCH .../inventory`로
**해당 일자의 총량을 0으로 내리는 것**이었다. 이것은 세 가지 운영 문제가
있었다.

1. **원래 총량을 잃어버린다.** 공사로 9월 25일~27일 판매를 멈추려면
   총량을 0으로 덮어써야 한다. 복구하려면 본사가 "원래 8실이었다"는 것을
   **기억하고 있어야** 한다. 재조정 대화상자는 표시된 전체 일자를 한 번에
   같은 값으로 덮기 때문에 공사 전날의 8실과 공사 기간의 0실을 **한 요청으로
   동시에 보낼 수도 없다**.
2. **매진과 판매 중지를 구분할 수 없다.** 둘 다 `remaining = 0`이라서
   직원 재고 화면도 "매진"이라고만 보여서, 본사가 의도적으로 멈춘
   구간인지 실제로 다 팔린 것인지 알 수 없었다.
3. **재고 0은 확정·보류 건수 때문에 내릴 수 없다.** 이미 확정 예약이
   있는 날짜의 총량은 409 `INVENTORY_CAPACITY_CONFLICT`로 거부된다.
   그래서 **판매를 멈추고 싶은 날짜에 이미 예약이 있으면 멈출 수
   없었다.**

그래서 **총량과 별개의 판매 중지 상태**를 뒀다. 지점 전체 판매 중지
(`PATCH /api/staff/hotels/{hotelId}/active`)와 같은 원칙으로, 중지는
**신규 판매만 막고 기존 예약을 그대로 둔다**.

## 서버 변경

### 판매 중지 구간 설정

- `PATCH /api/staff/hotels/{hotelId}/room-types/{roomTypeId}/sales-status`가
  객실 유형의 날짜 구간 판매 상태를 바꾼다. `HQ_ADMIN`만 허용하고 지점
  직원은 403, 잘못된 세션은 401, 멱원 키 누락은 400, 없는 지점·다른
  지점의 유형·없는 유형은 404다.
- 본문: `fromDate`·`toDate`(필수)·`status`(`OPEN`·`STOPPED` 중 하나).
  역순은 400, 기간은 최대 92일 초과 시 400, 그 외 상태값은 400이다.
- **총량은 건드리지 않는다.** `capacity`·`held`·`confirmed`를 그대로
  둬서 공사 뒤 원래 재고가 돌아오게 한다. 이것이 총량 0과의 핵심 차이다.
- **중지한 구간에 이미 확정·보류된 예약은 그대로 둔다.** 지점 전체 중지와
  같은 원칙이다. 취소는 전용 API가 있고, 중지가 예약을 취소하면 본사가
  고객에게 알리지 않은 채 환불 의무가 생긴다. 그래서 확정 2건이 있는
  날짜도 중지할 수 있다.
- **판매 중지는 신규 오퍼 생성만 막는다.** `AvailabilityService`의
  검색 쿼리에 `NOT EXISTS (... status = 'STOPPED')`를 붙여서, 중지한
  일자를 포함하는 검색에서 해당 유형의 오퍼를 뺀다. 고객이 "예약 가능한
  객실이 없습니다"를 보게 하되 오류가 아니다.
- **중지 구간 조회는 직원만 한다.** `GET /api/staff/hotels/{hotelId}/
  room-types/{roomTypeId}/sales-status`가 유형의 중지 구간을 돌려준다.
  `HQ_ADMIN`·`BRANCH_STAFF` 모두 자기 지점을 읽을 수 있다. SELECT만
  사용한다. 일자 단위로 저장한 상태를 연속된 구간으로 합쳐서 돌려준다.
- 멱원은 두 갈래로 동작한다. 같은 `Idempotency-Key` 재호출은 200에
  `created=false`로 같은 구간을 돌려주고, 응답 유실 뒤 새 키로 같은
  내용을 보내도 `staff_id`·지점·유형·시작일·종료일·상태의 SHA-256
  지문이 같아 같은 결과를 돌려준다.
- 응답은 `SalesStatusResponse(hotelId, roomTypeId, fromDate, toDate,
  status, stoppedDays, created)`다. `stoppedDays`는 해당 유형에서 현재
  `STOPPED`인 일자 수다.

### 재고 조회에 판매 상태 노출

- `InventoryView`의 각 일자에 `salesStatus`(`OPEN`·`STOPPED`)를
  추가했다. SELECT만 추가하므로 재고를 변경하지 않는다.
- 직원 재고 화면이 "매진"과 "판매 중지"를 구분하게 한다.

## 마이그레이션 변경

- V63 additive 마이그레이션이 `room_type_sales_status`·
  `room_type_sales_status_command` 표를 만든다.
  `(room_type_id, stay_date)`에 `status`를 둔다.
- `(hotel_id, staff_id, idempotency_key)` 유일 인덱스로 같은 멱원 키의
  중복 처리를 막고, `(hotel_id, staff_id, request_hash)` 유일 인덱스로
  같은 내용 재시도의 중복 처리를 막는다. 기존 `inventory_command`·
  `room_type_command`와 같은 구조다.
- **기존 표를 변경하지 않는다.** 라이브 DB의 3개 지점·4개 유형은
  영향을 받지 않는다. 중지 상태가 없으므로 모든 날짜가 `OPEN`이고
  고객 가용성도 바뀌지 않는다.

## 관리자 UI 변경

- `재고·가격` (`/dashboard/inventory`)의 그리드에 `판매 중지` 열을
  추가했다. 중지한 날짜가 있으면 **매진(빨강)과 다른 색(주황)**으로
  "중지"를 표시해서 본사가 의도적인 중지와 실제 매진을 구분하게 한다.
- `판매 중지` 버튼과 대화상자: 시작일·종료일. **현재 보이는 범위의
  첫날·마지막 날로 기본값을 채운다.** 서버 검증 실패 시 대화상자를
  닫지 않고 이유를 보여준다 (기존 패턴).
- 대화상자에 **현재 중지 구간 목록**과 `가장 이른 중지 구간 판매 재개`
  버튼을 추가했다. `getSalesStatus`로 읽어온다.
- **생성·수정은 매번 새 멱원 키를 쓴다** (다른 본사 버튼과 같은 패턴).
- 날짜 입력은 `type="date"`를 쓴다 (기존 범위 입력과 같은 패턴).
- `staff-api.ts`에 `getSalesStatus`·`setSalesStatus`를 추가했다.
  403·404·409 메시지를 구분한다.

## 미검증 항목 (사전 명시)

- **라이브 DB·compose 재빌드·브라우저 확인은 실행하지 않았다.**
  V63이 라이브에 적용되지 않았으므로 실제 중지 흐름은 사용자가 확인한다.
- **중지한 구간의 기존 예약에 대한 고객 안내는 이번 범위가 아니다.**
  중지가 예약을 취소하지 않으므로 본사가 기존 예약을 어떻게 처리할지는
  별도 정책이 필요하다.
- **재고 일괄 업로드(CSV)는 다음 항목이다.** 2번의 마지막 남은 항목이다.
- **판매 중지 구간의 요금은 그대로 둔다.** 중지가 요금을 건드리면
  재개 뒤 복구할 수 없으므로 총량과 같은 이유로 건드리지 않는다.
- **AI 예약 컨시어지가 중지 구간을 다루는지 확인하지 않았다.**
  AI는 가용성을 읽으므로 중지된 일자의 오퍼가 빠지는 것을 보게 되지만
  컨시어지 프롬프트 동작을 직접 검증하지는 않았다.
