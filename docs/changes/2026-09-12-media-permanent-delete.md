# CMS 미디어 자산 영구 삭제

## 변경 이유

V13의 미디어 보관은 공개 전달과 신규 참조만 막고 업로드 파일과 카탈로그 행은 유지했다. 더 이상 사용하지 않는 업로드를 안전하게 정리하되 실수와 경합으로 고객 콘텐츠가 손상되지 않도록 별도 영구 삭제 조건이 필요했다.

## 구현

- V19에서 `website_media_asset.archived_at`을 추가하고 기존 보관 자산은 `updated_at`으로 보정했다. 기존 서버와 함께 실행되는 구간을 고려해 필드는 nullable로 유지하며, 값이 없는 보관 자산은 삭제 대상이 아니다.
- 보관 시 `archived_at`을 기록하고 복원 시 비운다. 카탈로그 응답에는 보관 시각과 30일 뒤의 영구 삭제 가능 시각을 포함한다.
- 본사 전용 `DELETE /api/staff/website/media/{mediaId}`를 추가했다. 요청 버전이 일치하는 `UPLOADED`·`ARCHIVED` 자산 중 사용 위치가 없고 보관 후 30일이 지난 대상만 허용한다.
- 번들·활성·참조 중·유예 기간 안·오래된 버전 자산은 409 충돌로 거부한다.
- 실제 파일은 같은 저장 볼륨의 `.trash`로 먼저 이동한다. DB 트랜잭션이 롤백되면 원위치로 복구하고, 커밋되면 격리 파일을 제거한다. 정리 실패는 서버 오류 로그에 경로와 트랜잭션 상태를 남긴다.
- 관리자 미디어 선택기는 보관 자산의 삭제 가능일 또는 `영구 삭제 가능` 상태를 표시한다. 조건을 만족한 경우에만 확인 대화상자를 열어 삭제하며, 성공 뒤 목록과 선택 자산을 갱신한다.
- 홈페이지 문서에 선택적 `draftConnections`가 없을 때 편집기가 중단되던 기존 회귀도 빈 연결값으로 정규화해 복구했다.

## 검증

- 서버 TDD RED: 삭제 메서드 부재, 유예·자산 유형·참조 보호 누락, 롤백 복구 분기 제거 상태에서 각각 의도한 실패를 확인했다.
- `WebsiteMediaIntegrationTest` 14건 통과. 성공 삭제와 실제 파일 제거, 30일 유예, 활성·번들·참조 보호, 지점 권한, 버전 충돌, 트랜잭션 롤백 파일 복구를 확인했다.
- `WebContentIntegrationTest`, `WebsiteMediaIntegrationTest`, `WebsitePageIntegrationTest` 관련 회귀 44건이 통과했다.
- 관리자 CMS Chromium E2E 27건 통과. 영구 삭제 확인·요청 body·목록 제거, 유예 기간 버튼 비활성, 홈페이지 회귀를 포함한다.
- Docker API를 재빌드해 V19 적용과 `4080` 포트의 헬스 상태 `UP`을 확인했다. 실제 관리자 화면에서는 활성 자산 6건을 확인했고, 실제 사용자 자산에는 보관 또는 삭제 요청을 보내지 않았다.

## 다음 작업

미디어 파일 교체는 기존 자산을 덮어쓰지 않고 새 자산을 만든 뒤 사용 위치를 명시적으로 이동하는 별도 기능으로 구현한다.
