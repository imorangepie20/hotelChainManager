# 본사 지점 관리 - 지점 생성·지점 목록 조회 (2026-09-22)

> 상태: 작업 트리에만 있고 커밋하지 않은 상태.

## 변경 이유

`admin-menu-roadmap.md` 1번 `지점·객실 유형 관리`의 남은 항목 중 "지점 생성"을 구현했다. **본사가 지점을 만들 수단이 전혀 없었다.** 지점 행은 마이그레이션과 개발용 시드만 만들었고, 애플리케이션에서는 만들거나 읽을 수 없었다.

부수 결함이 하나 더 있었다. **관리자 화면의 지점 선택기가 3개 UUID를 하드코딩**하고 있었다. 서버에 지점이 생기거나 사라져도 화면이 따라가지 못했고, 환경마다 UUID가 다르면 선택기가 빈 상태로 남아 카탈로그·재고·보고서 화면이 동작하지 않았다.

## 서버 변경

- `POST /api/staff/hotels`가 새 지점을 만든다. `HQ_ADMIN`만 허용하고 지점 직원은 403, 잘못된 세션은 401, 멱원 키 누락은 400이다.
- **지점 행만 만들고 객실 유형·요금·재고를 심지 않는다.** 객실 유형 추가(`POST /api/staff/hotels/{hotelId}/room-types`)가 이미 기본 요금제와 90일분 일자 요금·재고를 같은 트랜잭션에 심으므로, 그 동작에 유형 시드를 맡긴다. 두 동작을 분리하면 시드 실패가 지점 생성을 롤백하지 않고, 본사가 빈 지점을 만들고 나서 채워 넣을 수 있다.
- **이름은 대소문자 구분 없이 중복을 거부한다.** 409 `HOTEL_NAME_CONFLICT`다. 지점 이름은 고객 웹·관리자 화면에서 지점을 식별하는 라벨이므로 중복을 허용하지 않는다. 삭제·이름 변경 수단이 아직 없으므로, 의도하지 않은 중복 생성이 들어가면 두 지점을 구분할 방법이 없다.
- **시간대를 서버가 검증한다.** `ZoneId.of`로 파싱해 보고 실패하면 400이다. 시간대는 재고 시드 시작일(지점 현지 날짜)과 취소 마감 시각의 기준이므로 잘못된 값을 저장하면 나중에 고칠 수 없다. 이미 만든 객실 유형의 시드 시작일이 틀어지기 때문이다.
- 멱원은 두 갈래로 동작한다. 같은 `Idempotency-Key` 재호출은 200에 `created=false`로 같은 지점을 돌려주고, 응답 유실 뒤 새 키로 같은 내용을 보내도 `staff_id`·이름·지역·시간대의 SHA-256 지문이 같아 같은 결과를 돌려준다. 동시 생성은 `hotel_command` 유일 인덱스가 막고 `DataIntegrityViolationException`을 잡아 저장된 지점을 돌려준다.
- 직렬화는 이름 충돌 검사와 insert 사이에 다른 트랜잭션이 끼어드는 것을 막기 위해 `select ... for update`를 쓴다. 지점은 체인 전체에 하나뿐이라 직렬화 범위가 객실 유형(지점 단위)보다 넓다.
- `GET /api/staff/hotels`가 지점 목록을 돌려준다. **SELECT만 사용**하고 상태를 변경하지 않는다. `HQ_ADMIN`만 허용하고 지점 직원은 403, 잘못된 세션은 401이다. 지점 직원은 자기 지점만 보면 되므로 전체 목록이 필요 없다.
- V59 additive 마이그레이션이 `hotel_command` 표를 만든다. **기존 표를 변경하지 않는다.**

## 관리자 UI 변경

- `호텔 및 객실` (`/dashboard/hotels`)의 **지점 선택기를 하드코딩에서 서버 조회로 바꿨다.** 지점이 추가되면 선택기에 바로 나타난다. 이전까지는 화면에 3개 지점이 고정이었다.
- 지점 선택기가 비었을 때 안내를 추가했다. 지점이 없으면 객실 유형 목록을 불러오지 않고, `지점 목록을 불러오는 중` 안내를 보여준다. 지점을 먼저 만들어야 한다는 흐름이 보이게 했다.
- `지점 추가` 버튼과 대화상자를 추가했다. `HQ_ADMIN`만 버튼이 보인다. 이름·지역·시간대를 받고, 범위·형식 판단은 서버에 둬서 서버 검증 메시지를 대화상자에서 볼 수 있게 했다. 다른 본사 화면과 같은 패턴이다.
- **빈 지점을 만들면 명시적으로 안내한다.** "객실 유형이 없으므로 고객 검색에 나타나지 않습니다"를 보여주지 않으면 본사는 지점을 만들고 예약이 안 되는 이유를 알 수 없다.
- 서버 검증 실패 시 대화상자를 닫지 않고 안내를 보여준다.

## 발견·수정한 결함

1. 테스트 두 개가 같은 본문으로 두 번째 요청을 보내면, 서버가 이를 멱원 재호출으로 판단해 200을 내려주는 것을 확인했다. **서버 동작은 올바르고 내 테스트 단정이 틀렸다.** 이름 중복 검증을 시험하려면 두 번째 요청이 다른 지역을 가져야 같은 멱원 지문이 아니다. 두 번째 요청의 지역을 바꿨다.
2. `@BeforeEach` 정리 순서가 잘못돼 세션이 남아 있었다. `staff_session`이 `staff_member`를 참조하고 `staff_member`가 `hotel`을 참조하므로 세션 → 직원 → 지점 순으로 지워야 한다. 이전 실행이 도중에 실패해 남은 행도 지우도록 정리를 idempotent하게 바꿨다.

## 미검증 항목

- **라이브 DB·compose 재빌드·브라우저 확인은 실행하지 않았다.** V59가 라이브에 적용되지 않았으므로 실제 지점 생성→객실 유형 추가→고객 검색 노출 흐름은 사용자가 확인한다.
- **지점 수정·판매 중지·삭제는 이번 범위가 아니다.** 삭제는 `room_type`·`reservation`·`reservation_change_request`·`website_page_room_type`·`staff_member` 외래키가 걸려 있어 안전한 삭제 조건을 따로 설계해야 한다. 본사가 실수로 지점을 지우면 예약 이력이 끊어진다.
- **지점 수정 수단이 없으면 이름 충돌을 풀 수 없다.** 중복 이름으로 만들기를 막았으므로, 오타이나 브랜드 변경으로 이름을 바꾸려면 현재 방법이 없다. 수정 API가 다음 항목이다.
- **빈 지점은 고객 검색에 나타나지 않는다.** 의도된 동작이지만, 본사가 지점을 만들고 객실 유형을 추가하기 전까지 `GET /api/availability`에 노출되지 않는다.
- **지점 목록의 정렬이 이름 오름차순으로 고정**이다. 지역·생성일 기준 정렬이나 페이징은 없다. 지점 수가 적을 때는 의미가 없다고 판단했다.
- **고객 웹의 지점 노출은 이번 범위가 아니다.** `GET /api/hotels`는 여전히 모든 지점을 반환한다. 빈 지점도 고객에게 보이지만 객실이 없으므로 예약할 수 없다.
