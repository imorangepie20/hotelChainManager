# 직원 예약자 정보 정정

## 변경 이유

예약 확정 후 이름이나 이메일의 오기를 발견한 직원이 예약의 가격·재고·결제 조건을 건드리지 않고 예약자 정보만 안전하게 정정할 수 있어야 한다.

## 구현 범위

- `CONFIRMED` 예약의 예약자 이름과 이메일만 수정한다.
- 본사 관리자 또는 예약 지점 직원만 API를 사용할 수 있다.
- 직원을 인증하고 입력을 검증한 뒤 예약 행을 잠가 지점 권한과 상태를 서버에서 다시 확인한다.
- 처리 직원까지 포함한 멱등 키 요청 지문으로 재시도를 식별하고, 기존값·변경값·처리 직원을 감사 이력에 기록한다.
- 예약 상세 안에서 수정하고 성공 시 상세를 닫은 뒤 목록을 갱신한다.

## 완료 기준

- 이름과 이메일은 trim 후 길이와 이메일 형식을 검증한다.
- 동일한 정보, 확정 이외 상태와 타 지점 요청은 변경·감사 기록 없이 거부한다.
- 동일 키·동일 요청은 최초 결과를 반환하고 감사 행을 중복 생성하지 않는다.
- 동일 키에 다른 요청을 보내면 멱등 충돌을 반환한다.
- 모바일과 키보드에서 수정, 오류 확인, 재시도와 저장 결과 확인이 가능하다.

## 제외 범위

- 날짜·객실 유형·요금제·객실 수·투숙 인원 변경
- 추가 결제·부분 환불
- 고객 직접 수정과 알림 이메일 발송

## 호환성과 롤백

- V30은 기존 예약 테이블을 변경하지 않고 `reservation_guest_change` 감사 테이블만 추가하므로 이전 애플리케이션 reader·writer와 함께 동작한다.
- 애플리케이션 롤백 시 감사 테이블은 남겨도 기존 동작에 영향이 없다. 제거가 필요하면 새 writer를 모두 내린 뒤 별도 migration으로 수행한다.
- 감사 이력에는 예약자 이름·이메일의 변경 전후 값이 포함된다. 이번 MVP는 자동 마스킹·삭제를 추가하지 않으며, 운영 보존·파기 정책이 확정되면 별도 migration과 배치로 적용한다.
- `staff_id` 외래 키는 감사 행이 남은 직원을 하드 삭제하지 못하도록 기본 제한 동작을 사용한다. 현재 운영에서는 감사 이력을 보존하는 동안 직원 레코드도 유지해야 한다.

## 검증 결과

- `StaffReservationGuestUpdateIntegrationTest` 8건 통과: 정규화·감사 기록, 동일 직원 재시도·충돌, 교차 직원 키 재사용 거부, 본사 권한, 인증 우선순위, 무변경·유효하지 않은 이메일 거부, 상태·타 지점 보존, HTTP 계약을 확인했다.
- 직원 운영·취소 회귀를 포함한 백엔드 대상 테스트 29건이 통과했다.
- 예약 관리 Chromium E2E 2건이 통과했다. 390×844에서 키보드 수정, 오류 노출, 동일 키 재시도, 성공 후 목록 갱신과 기존 취소 흐름을 확인했다.
- 변경 프런트 파일 ESLint, UI detector와 Next.js production build(정적 페이지 104개)가 통과했다.
- 실제 알림 이메일 발송, 운영 배포와 개인정보 보존·파기 자동화는 이번 범위에서 검증하지 않았다.
