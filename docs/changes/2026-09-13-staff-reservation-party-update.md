# 체크인 전 투숙 인원 변경

## 변경 이유

직원이 예약 확정 후 실제 투숙 인원이 달라진 경우 날짜·객실 유형·객실 수·가격을 건드리지 않고 성인과 아동 수만 바로잡을 수 있어야 한다.

## 구현 범위

- `CONFIRMED` 예약의 성인·아동 수만 변경한다.
- 성인은 1명 이상, 아동은 0명 이상이어야 하며 전체 인원은 `객실 유형 최대 수용 인원 × 예약 객실 수`를 넘을 수 없다.
- 본사 관리자 또는 예약 지점 직원만 처리하며 예약 행 잠금과 `Idempotency-Key`를 적용한다.
- 처리 직원, 이전·신규 성인·아동 수를 감사 이력에 기록한다.
- 예약 상세에서 인원을 변경하고 성공 시 목록을 다시 조회한다.

## 완료 기준

- 유효한 변경 뒤 예약과 감사 이력이 한 트랜잭션에서 갱신된다.
- 무변경, 허용 인원 초과, 잘못된 인원, 확정 이외 상태와 타 지점 요청은 예약과 감사 이력을 변경하지 않는다.
- 응답 유실 뒤 같은 요청을 재시도하면 동일 결과를 반환하고, 같은 키의 다른 요청이나 다른 직원 요청은 충돌한다.
- 모바일과 키보드에서 입력·오류 확인·재시도·성공 결과 확인이 가능하다.

## 제외 범위

- 날짜·객실 유형·요금제·객실 수·가격·결제 변경
- 체크인 이후 투숙객 추가·퇴실 및 투숙객별 신원 정보
- 수용 인원 초과 승인과 추가 요금

## 호환성과 롤백

- 기존 예약 테이블 구조는 변경하지 않고 감사 테이블만 추가한다.
- API와 UI를 되돌려도 기존 예약 조회·배정·취소 기능은 유지된다. 감사 테이블 제거는 운영 기록 보존 정책을 확인한 별도 migration으로 처리한다.

## 검증 결과

- `StaffReservationPartyUpdateIntegrationTest` 8건과 기존 `StaffReservationGuestUpdateIntegrationTest` 8건, 총 16건이 통과했다. 정상 변경과 감사 상세, 상태 변경 뒤 멱등 재시도, 동일 키의 다른 요청·직원 충돌, 잘못된 값·무변경·수용 인원 초과·확정 이외 상태·타 지점 거부, 본사 처리, HTTP 계약 및 기존 고객 정보 변경 회귀를 확인했다.
- HTTP 요청에서 성인·아동 필드 누락, `null`, 소수 입력을 400으로 거부하고 예약과 감사 이력을 변경하지 않는 회귀를 확인했다.
- 예약 관리 Chromium E2E 5건이 통과했다. 모바일 숫자 입력, 오류 표시, 값 변경 시 요청 키 교체, 동일 값 재시도 시 키 유지, 성공 뒤 목록 갱신과 기존 예약 관리 흐름을 확인했다.
- 변경 프런트 파일 ESLint와 UI detector가 통과했다.
- Next.js production build가 `/dashboard/reservations`를 포함한 정적 페이지 104개를 생성했다.
- 체크인 이후 인원 변경, 날짜·객실 유형·객실 수 변경, 추가 요금과 운영 규모 성능은 제외 범위이므로 검증하지 않았다.

## 다음 작업

- 날짜 또는 객실 유형 변경은 일별 재고와 가격 재계산·결제 차액 정책을 별도 설계한 뒤 진행한다.
