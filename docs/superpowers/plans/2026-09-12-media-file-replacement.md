# CMS 미디어 파일 교체 구현 계획

## 승인 범위와 설계

- 기존 파일·자산 UUID·전달 URL을 덮어쓰지 않고 기존 본사 전용 PNG/JPEG 업로드 API로 새 자산을 생성한다.
- 이미지 필드의 `파일 교체`에서 업로드한 새 자산만 교체 후보로 사용한다. 기존 이미지와 새 이미지를 비교하고 명시적으로 확인해야 현재 편집 위치에 적용한다.
- 페이지별 alt는 유지한다. 파일 내용에 맞는지는 관리자가 확인·수정한다.
- 적용은 현재 메모리 초안만 변경한다. 기존 초안 저장·발행 계약으로 usage를 갱신하며, 다른 위치·페이지·공개본·발행 snapshot·기존 파일은 자동 변경하지 않는다.
- 취소·업로드 실패는 현재 페이지를 변경하지 않는다. 업로드 후 취소한 새 자산은 카탈로그에 남고 기존 보관·삭제 정책으로 관리한다.
- 공통 MediaField와 미디어 선택기를 재사용해 지점·홈·일반 페이지·갤러리에 같은 흐름을 제공한다. 일괄 usage 이동·기존 파일 삭제·새 저장 API·DB migration은 범위 밖이다.

## 구현 순서

1. 관리자 직접 E2E 실패 테스트로 교체 확인·취소·오류·모바일·위치 한정을 고정한다.
2. 공통 이미지 필드와 선택기에 교체 모드를 추가한다.
3. 기존 서버 API의 새 자산 업로드·초안/공개 분리·usage·snapshot 보존을 대상 통합 테스트로 확인한다.
4. 변경 경로 E2E, TypeScript, 직접 lint와 로컬 API 읽기 검증을 실행한다.
5. 변경 이유·결과·미검증 항목을 한국어 변경 기록에 남긴다.

## 완료 기준

- 확인 전에는 이미지/alt와 페이지 저장·발행 상태가 바뀌지 않는다.
- 확인 후 현재 필드만 새 UUID/URL을 사용하고 alt는 유지된다.
- 저장 전 공개 영향이 없고 저장 후에도 명시적 발행 전에는 공개본이 유지된다.
- 기존 자산·파일·다른 페이지·과거 snapshot은 유지된다.
- 키보드 취소·포커스 복귀와 390×844 모바일 대화상자 사용을 확인한다.
- 실제 사용자 페이지·자산에는 검증용 저장·발행·보관·삭제 요청을 보내지 않는다.
