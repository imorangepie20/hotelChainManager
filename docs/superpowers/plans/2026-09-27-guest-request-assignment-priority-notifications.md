# 고객 요청 담당자·우선순위·유형별 알림 계획 (2026-09-27)

> 기준 문서: `docs/plans/admin-menu-roadmap.md` 6번 고객 요청 관리의 남은 항목.
> 요청에 적힌 `#step-4`는 현재 문서에서 운영 통계 절을 가리키므로, 충돌하지 않는 명시적 작업
> 설명(담당자·우선순위·알림)을 우선한다.

## 목표와 완료 기준

1. 본사 관리자와 지점 직원은 고객 요청 상세에서 허용된 담당자를 지정하고 `LOW`·`NORMAL`·`HIGH`
   우선순위를 바꿀 수 있다.
2. 본사는 모든 지점 요청을, 지점 직원은 자기 지점 요청만 조회·처리·알림 조회할 수 있다.
3. 고객 요청 접수 시 요청 유형에 맞는 앱 내 알림 한 건만 생성한다. 같은 접수의 재시도나 동시 요청은
   알림을 중복 생성하지 않는다.
4. 알림에는 고객 연락처·본문·처리 메모를 넣지 않는다. 요청 ID 일부, 지점, 유형별 라우팅 이름,
   접수 시각만 노출한다.
5. 담당자·우선순위 변경은 기존 멱등 명령과 append-only 감사 이벤트를 그대로 사용한다. 같은 키·같은
   본문은 재생하고 같은 키·다른 본문은 409이며, 권한 실패 시 요청·이벤트·명령을 모두 롤백한다.
6. 관리자 대화상자는 키보드로 열고 선택·저장·닫을 수 있으며 390px에서 가로 문서 넘침이 없다.

## 설계

- 알림은 외부 메일·푸시 provider로 보내지 않는 **인증 후 pull 방식의 앱 내 알림**으로 제한한다.
  별도 수신자·outbox 행을 만들지 않고 권한 범위의 `OPEN` 요청에서 직접 계산하므로 한 요청은 한 번만
  나타나며 전송 재시도 중복이 없다. 기존 `(hotel_id, status, created_at DESC)` 인덱스를 재사용하고
  최근 20건으로 제한해 공개 접수 남용이 외부 발송이나 무제한 관리자 payload로 확대되지 않게 한다.
- V68은 새 접수의 멱등 키를 독립 영수증으로 선점한다. 같은 키·같은 본문은 같은 요청을 반환하고,
  같은 키·다른 본문은 409로 거부한다. 기존 요청 행은 삭제·수정하지 않는다.
- V69는 요청 지문 중복 확인과 본사 전체 `OPEN` 알림 최신순 조회에 맞는 인덱스를 추가한다.
- `GET /api/staff/guest-requests/notifications`는 `OPEN` 요청의 알림만 최신순으로 반환한다. 본사는 전체
  지점, 지점 직원은 자기 지점으로 서버에서 범위를 고정한다.
- `GET /api/staff/guest-requests/{requestId}/assignees`는 요청 접근 권한을 먼저 확인한다. 본사 관리자는
  활성 본사 관리자와 요청 지점의 활성 지점 직원을, 지점 직원은 자기 지점의 활성 지점 직원만 본다.
  이메일·비밀번호 등 계정 관리 정보는 반환하지 않는다. transition도 같은 actor-aware 정책을 적용한다.
- 모든 고객 요청 조회 응답은 `Cache-Control: no-store`를 사용하고 처리 메모는 서버에서도 500자로
  제한한다. 접수에서 같은 멱등 키를 다른 본문에 재사용하면 409로 거부해 새 요청·알림이 생기지 않는다.
- 관리자 목록·상세에 우선순위를 표시하고, 별도 `담당·우선순위 변경` 대화상자가 기존 transition API를
  현재 상태와 함께 호출한다. 알림 패널은 유형별 한국어 라우팅 이름과 건수를 표시한다.
