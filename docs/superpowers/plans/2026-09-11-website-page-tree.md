# 고객 웹 페이지 트리·경로 발행 기반 구현 계획

최종 갱신: 2026-09-11

## 목적

현재 CMS는 호텔별 랜딩 콘텐츠 한 문서만 보관한다. 이 구조에는 사람에게 읽히는 주소, 메뉴 노출, 부모 페이지, 페이지별 발행 상태가 없으므로 슬러그 입력란만 추가해도 고객 URL과 메뉴에 연결되지 않는다.

이번 단계에서는 `website_page`를 고객 웹의 페이지·경로·메뉴·콘텐츠 발행 기준으로 도입한다. 기존 `hotel_web_content`는 삭제하거나 덮어쓰지 않고 이관 원본으로 남긴다. 기존 호텔 콘텐츠 API와 관리자 편집 API는 새 지점 랜딩 페이지를 읽고 쓰는 호환 경로로 유지한다.

## 완료 범위

### 데이터와 발행

1. `SECTION`과 `HOTEL_LANDING` 페이지를 보관하는 `website_page`를 추가한다.
2. 초안과 발행본에는 슬러그·경로·메뉴 설정·기존 랜딩 콘텐츠를 함께 보관한다.
3. 저장과 발행은 하나의 트랜잭션에서 콘텐츠와 페이지 메타데이터를 같이 갱신한다.
4. 저장·발행 낙관적 버전, 이력, 감사 로그를 페이지 단위로 기록한다.
5. 기존 3개 지점 랜딩을 다음 발행 경로로 한 번 이관한다.
   - `/stays/sokcho`
   - `/stays/seoraksan`
   - `/stays/jeju`
6. `/stays`는 메뉴 그룹용 `SECTION`으로 만들며, 첫 단계에서는 새 페이지 생성과 부모 이동은 제공하지 않는다.

### API와 권한

1. 공개 고객 API는 발행된 메뉴와 발행된 경로만 반환한다.
   - `GET /api/website/navigation`
   - `GET /api/website/pages/resolve?path=/stays/sokcho`
2. 본사 API는 페이지 트리 조회, 랜딩 초안 저장, 발행을 제공한다.
3. 모든 쓰기와 페이지 트리 조회는 `HQ_ADMIN`을 서버에서 검증한다. 지점 직원은 403을 받는다.
4. 기존 `/api/hotels/{hotelId}/content`와 `/api/staff/web-content/hotels/{hotelId}` 계열은 새 랜딩 페이지를 사용하는 호환 facade로 유지한다.
5. 가격·재고·예약·예약 토큰·개인정보는 페이지 콘텐츠나 URL에 저장하지 않는다.

### 관리자와 고객 웹

1. `/dashboard/website` 왼쪽 패널을 사이트 → 숙소 → 3개 지점 랜딩 페이지 트리로 교체한다.
2. 랜딩 편집기에는 경로 미리보기, 슬러그, 메뉴명, 메뉴 노출, 메뉴 순서를 추가한다. 기존 히어로·SEO·경험·오퍼·도착 안내 편집과 초안/발행 UX는 유지한다.
3. 고객 웹은 `/stays/:slug`을 공개 resolve API로 해석하고, 응답의 신뢰 가능한 `hotelId`로 기존 예약 검색을 연결한다.
4. 지점 예약 CTA는 `/stays/:slug#booking`을 유지한다. URL에 가격, 잔여 객실, 예약 토큰 또는 고객 정보는 넣지 않는다.

## 명시적 제외 범위

- 임의 페이지 생성·삭제, 드래그 앤 드롭 부모 이동
- 범용 블록 편집기, CTA 편집, 다국어 번역, 미디어 라이브러리
- 예약 발행, 승인 워크플로, 복원 UI
- canonical·OG·robots를 포함한 서버 렌더링 또는 prerender

이 항목들은 이번 데이터 모델 위에서 후속 단계로 구현한다. Vite 개발 서버의 history fallback은 동작하지만 실제 정적 배포 환경의 non-asset → `index.html` rewrite는 배포 단계에서 별도 구성·검증한다.

## 구현 순서

1. 기존 CMS 계약과 테스트를 조사하고, 지점 이관·공개 비노출·권한·충돌을 검증하는 서버 통합 테스트를 먼저 작성한다.
2. Flyway 마이그레이션으로 페이지·버전·감사 테이블을 추가하고 기존 3개 지점 콘텐츠를 복사한다.
3. 페이지 서비스와 공개/본사 컨트롤러를 구현하고 기존 콘텐츠 endpoint를 facade로 전환한다.
4. 관리자 API 타입과 페이지 트리를 추가하고, 메타데이터가 저장·발행 본문에 포함되는 E2E를 작성한다.
5. 고객 웹에 pathname 해석과 `/stays/:slug` 렌더링을 추가한다.
6. 변경 범위의 통합 테스트, 관리자 E2E, 고객 웹 빌드와 실제 deep link를 확인한다.
7. 구현·검증·남은 배포 fallback을 설계서·변경 기록·현재 개발 상태에 기록한다.

## 완료 기준

- 고객이 `/stays/sokcho`, `/stays/seoraksan`, `/stays/jeju`로 직접 접속하면 각 지점의 발행 랜딩과 해당 예약 바가 표시된다.
- 공개 navigation/resolve API는 초안 또는 미발행 경로를 반환하지 않는다.
- 본사가 변경한 슬러그·메뉴 설정과 콘텐츠는 같은 발행본 버전으로 공개된다.
- 잘못된·중복·예약어 슬러그, 지점 직원 변경, 오래된 저장·발행은 서버에서 거부된다.
- 기존 호텔 콘텐츠 조회와 기존 CMS 저장·발행 흐름은 새 랜딩 페이지 데이터와 동일한 발행본을 사용한다.

## 구현 결과

- [x] `V9__website_pages.sql`로 `website_page`, 페이지별 발행 버전, 감사 로그를 추가했다. 기존 `hotel_web_content`는 삭제하지 않고 이관 원본으로 보존한다.
- [x] 기존 3개 지점 랜딩은 `/stays/sokcho`, `/stays/seoraksan`, `/stays/jeju`로 이관한다. 개발 프로필의 반복 시드는 새 개발 DB에서도 이 세 랜딩을 생성한다.
- [x] 기존 호텔 콘텐츠 공개·초안·저장·발행 endpoint는 새 랜딩 페이지를 읽고 쓰는 호환 facade로 전환했다.
- [x] 공개 `navigation`, 공개 페이지 `resolve`, 본사 페이지 트리 endpoint를 추가했다. 공개 응답은 비어 있는 미발행 랜딩을 제외한다.
- [x] 관리자 CMS에 실제 페이지 트리, 슬러그·메뉴명·노출·순서 편집과 초안/발행 주소 상태를 추가했다.
- [x] 고객 웹은 `/stays/:slug`을 해석해 발행 페이지가 반환한 `hotelId`로 기존 예약 검색을 연결한다. 공개 메뉴에 노출된 지점 랜딩도 고객 헤더에서 직접 전환할 수 있다.

## 검증 결과

- 서버 통합 테스트: `WebContentIntegrationTest` 4건과 `WebsitePageIntegrationTest` 4건이 통과했다. 초안 경로의 공개 비노출, 발행 시 콘텐츠·메뉴·경로 동시 노출, 페이지 트리, 기존 초안과 발행본이 다른 이관 데이터의 공개 유지, 예약어·중복 슬러그 거부까지 확인했다.
- 관리자 Playwright: 페이지 트리 표시, 슬러그·메뉴명·순서 변경의 저장 요청 포함, 기존 콘텐츠·SEO·순서 변경·발행 방지 UX를 확인했다.
- 실제 API: API 4080 readiness `UP`, 3개 공개 지점 메뉴, `/stays/sokcho` resolve, 본사 페이지 트리 1개 그룹·3개 랜딩, 지점 직원의 페이지 트리 403을 확인했다.
- 고객 UI: 별도 브라우저 탭에서 `/stays/sokcho` 직접 접속 후 지점 히어로·예약 바·3개 지점 공개 메뉴·페이지별 제목을 확인했다.

## 남은 작업

- 실제 본사 로그인 UI에서 슬러그 또는 메뉴 설정과 콘텐츠를 저장·발행한 뒤, 새 주소의 고객 페이지까지 이어지는 비모킹 검증.
- 새 페이지 생성·삭제·부모 이동, 범용 블록·CTA·다국어·미디어, 인증 초안 미리보기, 예약 발행·복원.
- 정적 배포 환경의 history fallback과 페이지별 HTML SEO 렌더링.
