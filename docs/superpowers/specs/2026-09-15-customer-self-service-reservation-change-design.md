# 고객 직접 예약 변경 설계

상태: 사용자 승인 완료. 고객이 직원 승인이나 별도 링크 전달 없이 즉시 서버 견적과 정산을 거쳐 예약을 변경한다.

## 목적

확정 예약의 고객이 같은 브라우저의 예약 관리 token으로 날짜, 객실 유형, 요금제, 성인·아동 인원을 변경한다. Spring Boot가 재고, 수용 인원, 가격과 차액을 계산하며 기존 예약은 정산과 변경 적용이 끝날 때까지 유지한다.

예약 상세에 항상 보이는 `예약 변경` 진입점을 제공한다. 변경 가능한 상태가 아니면 버튼을 숨기지 않고 사유를 표시해 고객이 다음 행동을 알 수 있게 한다.

## 확정 정책

- 고객 직접 변경은 직원·본사 승인 단계를 거치지 않는다. 기존 직원 변경의 100,000원 승인 기준은 직원 흐름에만 유지한다.
- 대상 체크인은 오늘 이후여야 하며 서버의 지점 시간대와 변경 마감 정책을 적용한다.
- 한 예약에는 진행 중인 변경을 하나만 허용한다.
- 객실 수는 첫 버전에서 변경하지 않는다. 날짜, 객실 유형, 요금제, 성인·아동 인원만 변경한다.
- 추가금은 토스 테스트 결제 성공 후 적용한다. 차액이 0원이면 확인 직후 적용한다. 환불은 원 거래의 부분 환불 성공 후 적용한다.
- 결제나 환불 결과가 불명확하면 기존 예약을 유지하고 서버 상태 재확인을 제공한다.
- 고객 이메일·문자 발송은 포함하지 않는다. 같은 브라우저의 예약 상세가 변경과 결제의 진입점이다.

## 고객 흐름

1. 예약 상세에서 `예약 변경`을 누른다.
2. 기존 조건이 채워진 변경 화면에서 날짜와 인원을 정하고 서버에 가능한 객실·요금제를 조회한다.
3. 고객이 요금제를 선택하면 서버 견적이 기존·변경 조건, 총액, 차액, 환불 또는 추가 결제 방향과 만료 시각을 반환한다.
4. 고객이 `변경 확정`을 누르면 서버가 최신 가격과 재고를 다시 검증하고 대상 재고를 임시 확보한다.
5. 추가금은 같은 화면에서 토스 결제를 연다. 0원 또는 환불은 서버 처리 상태를 표시한다.
6. 적용 완료 후 예약 상세를 다시 읽어 변경된 일정, 객실, 인원과 결제 금액을 표시한다.

새로고침하면 서버의 활성 변경 상태를 복원한다. 결제 대기, 환불 처리, 적용 중에는 중복 요청 대신 현재 작업을 계속한다. 결제 전 활성 요청은 고객이 취소할 수 있다.

## 서버 경계

고객 API는 `X-Reservation-Token`으로 예약 소유권을 검증한다. 직원 session을 받거나 직원 계정을 대신 사용하지 않는다.

- `POST /api/reservations/{id}/change-quotes`: 날짜와 인원을 검증하고 자기 예약의 기존 재고를 고려한 객실·요금제 선택지와 차액을 반환한다.
- `POST /api/reservations/{id}/change-requests`: 견적 식별자·버전·선택 조건·예상 금액·멱등 key를 검증하고 고객 요청을 생성한다.
- `POST /api/reservations/{id}/change-requests/{requestId}/cancel`: 결제 전 고객 요청을 취소한다.
- 기존 `GET /api/reservations/{id}/change-summary`는 고객이 수행 가능한 action과 최신 상태를 함께 반환한다.
- 추가 결제는 현재 브라우저에 고객 결제 session cookie를 직접 설정한다. 공개 token 링크를 복사하거나 전달할 필요가 없다.

`ReservationStayQuoteService`, `ReservationChangeHoldService`, 결제·환불 gateway, outbox와 `ReservationChangeApplyService`를 재사용한다. 고객 orchestration 계층은 다음 순서만 소유한다.

1. 관리 token과 예약 상태 검증
2. 최신 재견적과 예상 금액 비교
3. 고객 요청 감사 기록과 자동 승인 기록
4. 재고 hold
5. 차액 방향별 결제·환불·적용 시작

## 데이터와 감사

기존 `reservation_change_request`에 요청 출처를 구분하는 `request_origin`을 추가한다. `STAFF`와 `CUSTOMER`만 허용하며 기존 행은 `STAFF`로 이관한다. 고객 요청은 직원 ID를 위조하지 않고 예약 ID와 token 검증 결과를 감사 이벤트에 남긴다. 원문 token, 결제 비밀값, 전체 개인정보는 저장하지 않는다.

견적에는 성인·아동 수 snapshot을 추가한다. 적용 transaction은 예약 일정, 객실 유형, 요금제, 인원, 일별 가격, 총액, 기존·대상 재고와 operation revision을 함께 변경한다.

## UI

- 예약 상세: `예약 변경`, 진행 상태, `추가 결제 계속하기`, `서버 상태 다시 확인`, 결제 전 `변경 요청 취소`.
- 변경 화면: 기존 조건 요약, 날짜 선택기, 인원 선택기, 서버 제공 객실·요금제 카드, 이전·변경 총액과 차액.
- 오류: 가격 변경은 새 견적을 표시하고 재확인을 요구한다. 품절, 수용 인원 초과, 마감 경과, 활성 요청 충돌은 서버 메시지와 돌아갈 경로를 표시한다.
- 모바일에서는 요약과 확정 action을 세로 배치한다. 대화상자와 날짜 선택기는 Escape, Tab 순환, 포커스 복귀를 지원한다.

## 실패와 복구

- 요청 timeout은 같은 멱등 key로 재시도한다.
- 추가 결제 실패나 취소는 기존 예약을 유지하고 확보 만료 전 재시도를 허용한다.
- PG 성공 여부가 불명확하면 자동으로 새 결제를 만들지 않고 조회를 반복한다.
- 환불 실패는 기존 예약을 유지한다. 성공한 환불을 중복 실행하지 않는다.
- 정산 성공 뒤 DB 적용 실패는 outbox가 재시도하며 한도 초과 시 본사 조정 상태로 남긴다.

## 검증

- API 단위·PostgreSQL 통합: token 접근 제어, 멱등 재시도, 가격 변경, 자기 재고 계산, 마지막 객실 경합, 인원 수용 한도, 활성 요청 충돌.
- 정산: 추가 결제, 0원, 부분 환불, 실패, UNKNOWN, 만료와 적용 재시도에서 기존 예약 보존 및 정확히 한 번 적용.
- 고객 계약: 상세 진입 버튼, 견적 비교, 새로고침 복원, 상태별 action, 한국어·영어 문구.
- 타입 검사와 production build.
- 브라우저 검증은 사용자 범위로 남기고 데스크톱·모바일·키보드 체크리스트를 변경 기록에 제공한다.

## 완료 조건

- 확정 예약 고객이 예약 상세에서 별도 직원 작업 없이 변경을 시작할 수 있다.
- 서버 견적 이외의 금액이나 품절 객실로 변경을 확정할 수 없다.
- 추가 결제·0원·환불 경로가 성공한 경우에만 예약과 재고가 정확히 한 번 변경된다.
- 실패·불명확 상태에서는 기존 예약이 유효하며 고객이 현재 상태와 복구 action을 확인할 수 있다.
- 변경 완료 후 예약 상세에 새 일정, 객실, 인원과 총액이 표시된다.
