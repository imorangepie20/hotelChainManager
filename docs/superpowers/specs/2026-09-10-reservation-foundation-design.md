# 첫 단계: 예약 기반 설계

상태: 검토용. 사용자 제공 범위를 구체화한 설계이며 구현 완료 문서가 아니다.

## 범위와 산출물

전체 개발 순서는 예약 → 직원 운영 → 다지점·본사 → AI → 다국어·모바일 완성이다. 첫 구현은 한 지점에서 검색·객실 선택·임시 확보·모의 결제·예약 조회·취소까지 실제 PostgreSQL과 연결한다. 최종 MVP는 국내 속초·설악산·제주도 3개 지점이다. 속초와 설악산은 별도 지점으로 관리한다.

고객 웹 `apps/web/`, Spring Boot `services/api/`, 후속 AI `services/concierge/`로 구성한다. 관리자 앱은 제공된 `SDTPL_ADM/`에서 발전시킨다. Docker Compose 구성은 루트에 둔다. 고객 디자인은 관리자 테마와 별도로 구성하며 구체적 브랜드·사진 선택은 고객 UI 단계에서 다룬다.

## 서비스 책임

Spring Boot 내부에 hotel, inventory, pricing, reservation, payment, operations, identity 모듈을 둔다. 첫 단계에서는 예약에 필요한 모듈을 구현한다. AI 서비스는 이후 Spring Boot의 조회 API를 사용한다. 관리자 Next.js 서버에 별도 재고 계산이나 예약 확정 로직을 만들지 않는다.

## 데이터

- Hotel: 지점·지역·시간대.
- RoomType: 지점·수용 인원·설명. 실제 Room 번호는 운영 단계에서 별도로 관리.
- RatePlan: 조식 여부·취소 정책과 일별 요금 규칙.
- InventoryDay: 객실 유형·날짜의 판매 수량, 확보 수량, 확정 수량. 객실 유형·날짜 고유 제약.
- Reservation: 날짜·인원·수량·상태·확보 만료 시각·예약자 정보. 일별 금액과 정책 스냅샷 포함.
- PaymentAttempt: 예약·멱등 키·요청 결과·테스트 결제 상태.

금액은 KRW 정수로 처리한다. 검색은 최신 참고 견적이며 확보 시 가격을 재계산한다. 가격이 달라졌으면 고객이 변경 내용을 확인한 뒤 진행한다. 숙박 날짜는 지점 기준, 만료 시각은 UTC로 저장한다.

## 상태와 트랜잭션

예약 상태: PENDING_PAYMENT → CONFIRMED 또는 EXPIRED. CONFIRMED → CANCELLED. NO_SHOW와 실제 투숙 상태는 운영 단계에서 추가한다.

확보 요청은 날짜 범위·인원·수량을 검사하고 필요한 InventoryDay 행을 날짜 순서로 잠근다. 모든 날짜의 판매 가능 수량이 충분해야 확보 수량을 증가시키고 예약을 생성한다. 누락된 재고 행은 판매 불가다. 제안 확보 시간은 10분이다.

결제·만료·취소는 예약 행을 먼저 잠그고, 이어 동일한 날짜 순서로 재고 행을 잠근다. 모든 변경 경로에서 같은 잠금 순서를 유지한다. 결제 확정 시 만료를 재검사하고 확보 수량을 확정 수량으로 이동한다. 만료 작업과 요청 시 만료 검사 모두 같은 전이 함수를 사용해 한 번만 반환한다.

예약 생성·결제·취소 요청에 멱등 키와 요청 내용 해시를 저장한다. 같은 키의 다른 요청은 충돌로 반환한다. 외부 PG는 첫 단계에 연결하지 않는다. 모의 결제 성공·실패·반복 요청을 지원하고 화면에 테스트임을 표시한다.

취소 가능 여부와 환불 금액은 예약에 저장한 정책으로 계산한다. 확정 예약 취소 시 해당 일자 재고를 한 번만 반환한다. 테스트 환불 실패 시 취소 완료로 표시하지 않는다. 실제 PG 도입 시 비동기 환불 상태와 재처리를 별도 설계한다.

## API와 접근

- GET /api/hotels: 지점 목록.
- GET /api/availability: 지점·날짜·성인·아동·객실 수로 검색.
- POST /api/reservations: 견적 확인과 임시 확보.
- POST /api/reservations/{id}/test-payment: 모의 결제.
- GET /api/reservations/{id}: 권한 있는 예약 조회.
- POST /api/reservations/{id}/cancel: 취소 처리.

예약 번호만으로 개인정보를 조회할 수 없다. 첫 단계 비회원 예약은 브라우저가 32바이트 난수 관리 토큰을 만들고 `X-Reservation-Token` 헤더로 전달한다. 서버는 원문을 반환하거나 저장하지 않고 SHA-256 해시만 저장한다. 생성 요청은 같은 토큰과 `Idempotency-Key`를 다시 보내면 응답 유실 뒤에도 같은 예약을 조회할 수 있다. 토큰은 URL과 로그에 넣지 않는다. 다른 기기에서의 복구·이메일 발송은 후속 인증 단계에 포함한다.

입력 오류는 400, 접근 거부는 403 또는 존재 은폐용 404, 재고·상태·멱등 키 충돌은 409로 구분하고 사용자 메시지와 오류 코드를 반환한다.

## 완료 검증

실제 PostgreSQL 통합 테스트로 마지막 1객실의 동시 확보 시 하나만 성공하는지 확인한다. 여러 숙박일 중 하나라도 부족하면 전체 변경이 롤백되어야 한다. 결제와 만료 경합, 중복 결제·취소, 정책 스냅샷 보존, 타 예약 접근 차단을 검증한다.

브라우저에서 날짜·인원 입력 → 객실 선택 → 예약 정보 → 테스트 결제 → 완료 → 조회·취소를 검증한다. 재고 부족·결제 실패·확보 만료 화면과 모바일 키보드 접근도 확인한다. 설치·빌드·마이그레이션 명령은 구현 시 실제 실행 가능한 상태로 제공한다.
