# 고객 예약·변경 UX 재설계

상태: 구현 전 설계. 고객 화면을 먼저 완성하고 실제 결제 검증은 마지막에 수행한다.

## 문제

현재 고객 웹은 브랜드 홈의 예약 바 아래에 검색 결과, 예약자 입력, 결제, 예약 상태를 계속 이어 붙인다. 사용자는 검색 후 화면이 어디에 생겼는지 찾아야 하고, 예약 단계와 일반 콘텐츠가 섞이며, 결제 결과에서 다음 행동도 분명하지 않다. 예약 조회는 현재 브라우저 세션에 의존하고 예약 변경은 직원 API와 단독 결제 페이지만 있어 사용자가 변경 링크를 받는 과정이 화면에 없다.

기능 단위 테스트를 먼저 진행하면서 실제 사용자 여정이 완성되지 않은 상태에서 결제 검증까지 진행한 것도 문제다. 앞으로는 화면과 연결 동선을 먼저 완성하고, 계약 테스트와 모의 상태 검증 후 실제 토스 테스트 결제를 마지막에 한 번 검증한다.

## 목표

- 메인은 호텔 탐색과 예약 검색 시작점으로 사용한다.
- 검색 이후에는 전용 예약 화면에서 한 단계씩 진행한다.
- 사용자는 현재 단계, 선택 내용, 총액, 다음 행동을 항상 확인할 수 있다.
- 예약 완료 후 조회·취소·변경 결제까지 같은 시각 체계와 정보 구조를 사용한다.
- 가격, 재고, 예약 확정, 변경 차액은 Spring Boot 응답만 표시한다.
- 데스크톱과 모바일에서 동일한 순서와 의미를 유지한다.

## 목표 사용자 여정

### 신규 예약

1. 홈에서 지점, 체크인·체크아웃, 인원, 객실 수를 입력한다.
2. `객실 검색`을 누르면 `/booking/results`로 이동한다.
3. 검색 결과에서 객실 사진, 주요 특징, 요금제, 취소 조건, 숙박 총액을 비교한다.
4. 객실을 선택하면 `/booking/checkout`에서 선택 요약과 예약자 정보를 확인한다.
5. 서버가 객실을 임시 확보한 뒤 같은 화면에서 남은 확보 시간과 결제 버튼을 보여준다.
6. 결제 성공 후 `/booking/complete`에서 예약 번호와 예약 관리 진입점을 제공한다.

### 예약 조회와 취소

1. 헤더의 `예약 조회`는 `/reservations`로 이동한다.
2. 같은 브라우저에서 만든 예약은 목록으로 바로 보여준다.
3. 다른 기기 복구는 예약 완료 이메일의 보안 링크를 사용한다. 예약 번호만으로 개인정보를 열지 않는다.
4. 상세 화면 `/reservations/:id`는 일정, 객실, 인원, 결제 상태, 취소 정책과 가능한 행동을 보여준다.
5. 취소는 예상 환불액을 먼저 확인하고 별도 확인 대화상자에서 실행한다.

### 예약 변경과 추가 결제

첫 버전의 변경 요청 생성 권한은 기존 정책대로 직원에게 둔다. 사용자는 호텔에 변경을 요청하고 다음 순서로 처리한다.

1. 직원이 관리자 예약 상세에서 새 일정과 객실을 선택한다.
2. 서버가 재고, 최신 가격, 차액과 승인 필요 여부를 계산한다.
3. 추가 결제가 필요하면 관리자 화면에 `고객 결제 링크` 카드가 나타난다.
4. 직원은 `이메일 전송` 또는 `링크 복사`를 사용한다. 이메일 연동 전 로컬 환경에서는 링크 복사만 제공하고 이를 테스트 전용이라고 표시한다.
5. 사용자가 받은 링크를 열면 `/reservation-change-payment`에서 기존 예약과 변경 내용을 나란히 비교한다.
6. 사용자는 변경 일정, 객실, 요금제, 기존 총액, 신규 총액, 추가 결제액을 확인한 뒤 결제한다.
7. 결제 성공 후 변경 완료 화면으로 전환하고 예약 상세로 이동할 수 있다.
8. 감액 변경은 직원이 환불을 시작하며, 사용자는 예약 상세에서 환불 금액과 진행 상태를 확인한다.

자동 이메일 발송은 전달 어댑터와 outbox를 추가한 뒤 활성화한다. 공급자 키가 없는 개발 환경에서는 실제 발송을 흉내 내지 않고 관리자 화면에서 테스트 링크를 명시적으로 제공한다.

## 화면 구조

### 홈 `/`

- 브랜드 콘텐츠와 예약 검색 바만 유지한다.
- 검색 결과, 예약자 입력, 결제 상태, 예약 관리 카드는 홈에 렌더링하지 않는다.
- 예약 바는 선택한 조건을 URL 검색 매개변수로 전달한다.
- AI 예약 도우미가 조건을 적용해도 최종 동작은 같은 검색 결과 화면으로 이동한다.

### 객실 검색 `/booking/results`

- 상단에 검색 조건 수정 바와 검색 결과 개수를 둔다.
- 객실 유형별 카드 안에서 요금제를 비교한다.
- 카드에는 숙박 전체 총액을 우선 표시하고, 세금 포함 여부와 객실 수·박 수를 함께 표시한다.
- 선택한 객실은 우측 요약 패널에 고정한다. 모바일에서는 하단 고정 요약과 `다음` 버튼을 사용한다.
- 검색 조건이 바뀌면 기존 선택을 해제하고 서버에서 다시 조회한다.
- 매진, 가격 변경, 검색 오류, 결과 없음은 각각 별도 상태로 표시한다.

### 예약·결제 `/booking/checkout`

- 단계 표시는 `객실 선택 → 예약 정보 → 결제` 세 단계만 사용한다.
- 왼쪽에는 예약자 이름·이메일 입력과 정책 동의, 오른쪽에는 선택 요약과 총액을 둔다.
- `예약 및 결제 진행`을 누를 때 서버가 가격과 재고를 다시 확인하고 10분 확보를 생성한다.
- 확보 성공 후 입력 필드를 잠그고 남은 시간을 표시하며 토스 결제 버튼을 활성화한다.
- 결제창을 닫거나 실패하면 같은 확보 건에서 다시 시도할 수 있다.
- 확보가 만료되면 결제 버튼을 제거하고 검색 결과로 돌아가도록 안내한다.

### 예약 완료 `/booking/complete`

- 성공 여부와 예약 번호, 일정, 객실, 결제 금액을 한 화면에서 확인한다.
- `예약 상세 보기`와 `홈으로` 두 행동만 제공한다.
- 서버 확인 중에는 중복 결제를 경고하고 자동 재조회한다.
- 실패 화면은 오류 코드 대신 사용자가 취할 행동을 먼저 안내한다.

### 예약 목록·상세 `/reservations`, `/reservations/:id`

- 예약 상태를 `결제 대기`, `예약 확정`, `변경 처리 중`, `취소 처리 중`, `취소 완료`, `만료`로 번역한다.
- 상세 화면의 행동은 서버가 반환한 가능 action만 표시한다.
- 진행 중인 변경이 있으면 별도 진행 카드에서 승인, 결제, 환불, 완료 상태를 보여준다.
- 추가 결제 링크가 현재 세션에 연결돼 있으면 `추가 결제 계속하기`를 제공한다.

### 예약 변경 결제 `/reservation-change-payment`

- 기존 조건과 변경 조건을 두 열로 비교하고 바뀐 항목을 강조한다.
- 추가 결제 금액, 링크 만료 시각, 취소 정책 영향을 결제 버튼 바로 위에 표시한다.
- 결제 성공, 처리 중, 실패, 만료를 같은 페이지 상태로 제공한다.
- 링크 토큰은 fragment로 받은 뒤 즉시 제거하고 HttpOnly 고객 세션으로 교환한다.

## 공통 UX 규칙

- 예약 단계 화면에는 브랜드 콘텐츠, 오퍼, AI 패널을 섞지 않는다.
- 주요 행동 버튼은 화면마다 하나만 강조한다.
- 금액은 모두 `객실 수 × 숙박 기간`의 총액으로 표시한다.
- 로딩 중에는 버튼 문구만 바꾸지 않고 해당 영역의 진행 상태를 함께 알린다.
- 오류 메시지는 원인, 현재 보존된 상태, 다음 행동 순서로 작성한다.
- 테스트 결제에는 모든 결제 화면 상단에 실제 과금이 없음을 표시한다.
- 모바일 390px에서 가로 스크롤 없이 동작하고 하단 고정 버튼이 콘텐츠를 가리지 않아야 한다.
- 달력, 대화상자, 선택 메뉴는 기존 기능성 컴포넌트를 사용하고 키보드와 포커스 복귀를 확인한다.

## 기술 구조

현재 `App.tsx`에 모인 검색, 선택, 확보, 결제, 예약 관리 상태를 경로별 페이지와 공통 예약 상태 저장소로 분리한다. API 호출은 기존 `apps/web/src/lib/api.ts`를 통해 유지하고 페이지 컴포넌트가 가격이나 상태 전이를 계산하지 않는다.

예상 구성은 다음과 같다.

- `booking-search-page`: 검색 조건과 결과 조회
- `room-results`: 객실·요금제 비교와 선택
- `booking-checkout-page`: 예약자 입력, 임시 확보, 결제 시작
- `booking-result-page`: PG 반환 뒤 서버 상태 확인
- `reservation-list-page`, `reservation-detail-page`: 예약 관리
- `reservation-change-payment-page`: 변경 비교와 추가 결제
- `booking-session`: 같은 브라우저의 예약 관리 토큰과 진행 중 선택을 저장

페이지 새로고침과 뒤로 가기를 지원하되 관리 토큰은 URL, 로그, 분석 이벤트에 넣지 않는다. 검색 조건만 URL에 저장하고 예약자 정보와 결제 정보는 저장하지 않는다.

## 개발 순서

1. 경로와 공통 예약 레이아웃을 만들고 홈에서 인라인 검색 결과와 예약 패널을 제거한다.
2. 검색 결과 화면과 검색 조건 수정, 객실 비교·선택을 완성한다.
3. 예약자 입력, 임시 확보, 결제 시작 화면을 완성한다.
4. 결제 완료·실패·확인 중 화면과 새로고침 복구를 완성한다.
5. 예약 목록·상세·취소 화면을 완성한다.
6. 관리자 변경 요청 화면에 결제 링크 복사·전달 상태를 연결한다.
7. 고객 변경 결제 화면을 비교 중심으로 재구성하고 예약 상세에 진행 상태를 연결한다.
8. 모든 UI 상태와 API 계약 검증이 끝난 뒤 실제 토스 테스트 결제와 부분 환불을 검증한다.

## 검증 순서

구현 중에는 변경한 페이지의 컴포넌트 테스트, API 계약 테스트, TypeScript와 production build만 실행한다. 화면이 모두 연결되기 전에는 실제 PG 결제를 반복하지 않는다.

완성 후 다음 순서로 한 번의 실제 사용자 시나리오를 검증한다.

1. 홈 검색 → 결과 조건 일치
2. 객실 선택 → 예약자 입력 → 10분 확보
3. 토스 테스트 결제 → 예약 확정 → 새로고침 복구
4. 예약 상세 → 직원 변경 요청 → 고객 링크 전달
5. 고객 추가 결제 → 디럭스 객실 변경 확정
6. 감액 변경 → 토스 부분 환불 → 예약·재고·거래 대조
7. 데스크톱과 390×844 모바일에서 키보드, 포커스, 오류·만료 상태 확인

## 완료 기준

- 홈에는 검색 시작 기능만 있고 객실 카드와 예약 패널이 나타나지 않는다.
- 검색부터 결제 완료까지 사용자가 이전·현재·다음 단계를 이해할 수 있다.
- 새로고침과 결제창 닫기 이후에도 같은 예약을 안전하게 계속할 수 있다.
- 예약 상세에서 변경·환불 진행 상태와 사용자가 해야 할 행동을 확인할 수 있다.
- 직원이 추가 결제 링크를 복사하거나 전송하는 명확한 화면이 있다.
- 실제 결제 성공 뒤 예약, 재고, 원승인 거래가 일치한다.
- 실제 증액·감액 변경 뒤 예약, 재고, 추가 결제 또는 부분 환불이 일치한다.
- 모바일과 키보드 사용에서 예약을 끝까지 완료할 수 있다.

## 제외 범위

- 회원 가입과 소셜 로그인
- 운영 이메일 공급자 계약과 실제 문자 발송
- 저장 카드와 간편결제 계정 관리
- OTA 예약 변경
- 체크인 이후 고객 셀프 변경
- AI의 예약 생성·결제·변경 실행
