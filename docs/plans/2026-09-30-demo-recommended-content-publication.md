# 가상 호텔 추천 상세 콘텐츠 운영 발행 계획

## 승인 및 범위

사용자는 지점별 상세 콘텐츠 생산·입력과 한국어 9개 발행을 승인했다. Aside의 본사 로그인 세션을 해당 탭 안에서 사용하며 세션 토큰·자격 증명을 외부로 복사하거나 문서에 기록하지 않는다. 콘솔 붙여넣기 허용은 사용자에게 별도로 승인받았다.

이번 추가 요청으로 SECTION 보완의 커밋·푸시·Zorin 운영 배포와 실제 한국어 데모 상세 9개 발행을 함께 승인했다. 검증된 clean commit archive만 배포하며 배포 전 운영 PostgreSQL 논리 백업, 소스 SHA-256·컨테이너 health·공개 API 확인을 수행한다. 이후 운영 관리자 인증 세션 안에서만 상세·추천을 등록하고 각 쓰기의 정확한 대상을 다시 읽는다. 인증 세션이 없으면 로그인을 요청하며 DB 직접 삽입이나 토큰 복사를 하지 않는다.

## 콘텐츠 구성과 작성 기준

- 속초: DINING 파도 테이블, FACILITY 오션 라운지, EXPERIENCE 해변 산책.
- 설악산: DINING 숲의 식탁, FACILITY 포레스트 라운지, EXPERIENCE 숲길 산책.
- 제주: DINING 돌담 키친, FACILITY 선셋 라운지, EXPERIENCE 해안 산책.
- 모두 STAY HANEUL 가상 호텔 데모 콘텐츠로 명시한다. 가격·재고·예약 가능 여부·확정 영업시간·실제 제공 상품은 생성하지 않는다.
- 기존 지점 이미지 자산을 재사용하고, 풍경 이미지를 실제 식당·시설 사진처럼 설명하지 않는다. 소개, 제안하는 머무름, 이용·안전 안내를 구체적으로 작성한다.

## 실행 순서

1. 인증된 CMS API에서 페이지 트리, 이미지 카탈로그, 랜딩 초안·발행본을 읽고 기존 데이터와 충돌 여부를 확인한다.
2. 지점 소유 SECTION이 없으면 정상 관리 API·UI로 메뉴 비노출 섹션을 먼저 생성한 뒤 해당 섹션 아래 한국어 상세 3개씩 생성한다. HOTEL_LANDING을 직접 부모로 사용하지 않는다. 기존 콘텐츠를 덮어쓰지 않으며 저장 문서와 발행 버전을 별도 조회한다.
3. 상세 9개의 공개 resolve와 이미지 응답을 검증한 다음 랜딩 추천 관계를 DINING → FACILITY → EXPERIENCE 순으로 저장하고 발행한다.
4. 랜딩의 다른 콘텐츠·이미지·관계를 보존하고 초안·발행 차이가 있으면 기존 미발행 변경을 함께 발행하지 않는다.
5. 상세 9개와 랜딩 3개의 CMS read-back, 공개 API의 추천 순서·경로·문구·이미지를 프로그램으로 집계한다. 고객 브라우저에서 카드 클릭 및 상세 렌더링을 직접 확인한다.

## 재개 체크포인트

- 인증된 CMS API로 구조 SECTION 3개와 한국어 상세 9개를 생성·발행했다. 세 랜딩에 `MANUAL_CARD` 연결을 식음→시설→체험 순으로 저장·발행했고 원본 콘텐츠 보존 및 공개 snapshot 3개씩을 확인했다.
- 공개 resolve·컬렉션·이미지 200 확인 후 고객 브라우저에서 `/stays/sokcho/discover/pado-table`이 PAGE NOT FOUND였다. 고객 라우터가 4단계 상세의 SECTION slug를 `rooms|dining|facilities|experiences`로 제한하지만 서버는 사용자 정의 slug를 지원하는 계약 불일치다.
- 보완 설계: `/stays/{hotelSlug}/{sectionSlug}/{detailSlug}`만 일반 CMS 상세로 해석한다. 컬렉션 우선순위·영어 locale·slug 유효성·4단계 제한·구조 SECTION의 공개 거절은 유지한다. 한국어/영어 회귀 테스트 RED→GREEN, 고객 타입/빌드, 고객 웹만 커밋 기반 재배포, 운영 상세 9개 카드 이동·제목·데모 고지·이미지 렌더가 완료 기준이다. API·관리자·DB는 다시 빌드하지 않는다.

- 사용자가 Chrome 운영 본사 로그인을 준비했다. 연결된 CMS 탭에서 HQ_ADMIN, 실제 카탈로그 3지점·미디어 31개·상세 0개를 확인했다. 세 랜딩의 초안/발행 콘텐츠·메타데이터·연결이 모두 일치해 미발행 변경을 함께 발행할 위험이 없다.
- 각 지점에 비노출 `discover` SECTION을 만든 뒤 승인된 상세 3개를 생성·발행한다. 신규 상세의 고객 메뉴 노출도 false이며 랜딩 카드와 공개 경로로 접근한다. 식음 유형의 필수 운영 시간 블록은 `가상 데모 · 실제 운영 없음`으로 명시하고 closed=true·시간 값 없음으로 넣어 확정 영업시간을 만들지 않는다. 시설은 운영 시각 대신 SPEC_TABLE 안내를 사용한다.

- 지점 SECTION 생성 경로 누락을 보완하는 API·관리자 UI를 로컬에 구현했다. SECTION SQL 준비 없이 생성 → 상세 발행 → 랜딩 추천 발행 → 공개 resolve 흐름을 실제 테스트 DB에서 검증했다.
- 추가 승인에 따라 기능 커밋 `b6e5049`의 커밋·푸시·CI success·운영 API/관리자 배포와 source manifest·health 검증을 완료했다. 생성 경로가 운영 이미지에 포함됐지만 인증된 운영 UI/API 쓰기 검증은 아직 하지 않았다.
- 실제 한국어 상세 9개 생성·발행과 랜딩 추천 3개씩 입력은 운영 HQ_ADMIN 브라우저 로그인 세션 미연결로 미완료다. 공개 컬렉션 9조합은 모두 0개, 세 랜딩 추천은 0개다. 사용자 로그인·브라우저 연결 준비 요청은 시간 초과됐다. 토큰 복사·DB SQL 삽입으로 우회하지 않고 인증 세션이 준비되면 재개한다. 영어 발행을 자동으로 수행하지 않는다. 검증·제약은 [섹션 생성 변경 기록](../changes/2026-09-30-cms-section-creation-gap.md)을 따른다.

## 운영 발행 완료 기준

한국어 상세 9개와 지점별 추천 3개가 실제 운영에 발행되고 공개 경로로 해석되어야 한다. 운영 쓰기 응답이나 SPA HTML 200만으로 완료 처리하지 않는다. 결과·정확한 페이지 ID/경로·미검증 범위를 변경 기록과 현재 개발 맥락에 반영한다. 영어 번역 발행은 범위 밖이다. 추가 승인에 따른 소프트웨어 커밋·푸시·배포와 콘텐츠 발행은 별도 완료 상태로 기록한다.
