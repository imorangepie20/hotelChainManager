# 본사 재고·가격 - 재고 일괄 업로드(CSV) (2026-09-24)

> 상태: 작업 트리에만 있고 커밋하지 않은 상태.

## 변경 이유

`admin-menu-roadmap.md` 2번 `재고·가격`의 **마지막 남은 항목**이다. 1번
영역(지점·객실 유형 관리)과 2번의 판매 중지 구간 설정이 완료됐으므로
로드맵 순서(1 → 2 → 3 → 5 → 4 → 7 → 6 → 8)에 따라 2번을 마무리한다.

현재 본사가 여러 날짜의 재고를 바꾸려면 **`PATCH .../inventory`로
날짜마다 일일이 입력**해야 한다. 재고 대화상자는 표시된 전체 숙박일을
**하나의 같은 총량값으로 덮어버린다**. 그래서 실제 운영에서 자주 생기는
"주말은 6실, 평일은 8실, 공사 주간은 0실" 같은 **날짜별로 다른 재고를
한 번에 반영할 수 없다**. 본사는 90일분 재고를 바꿀 때 대화상자를
여러 번 띄워야 하고, 어느 날짜를 덮었는지 직접 기억해야 한다.

CSV 내보내기·업로드는 이미 본사 화면 두 곳(감사 이력·운영 통계)에서
쓰고 있는 패턴이다. 재고에는 이 패턴을 **읽기와 쓰기 양쪽으로** 적용한다.

## 서버 변경

### CSV 내보내기

- `GET /api/staff/hotels/{hotelId}/inventory/export`가 객실 유형별
  일자 재고를 CSV로 내려준다. `HQ_ADMIN`만 허용하고 지점 직원은 403,
  잘못된 세션은 401, 없는 지점은 404다.
- 쿼리 파라미터 `from`·`to`를 받고 기본값은 오늘 ~ 13일 뒤, 최대 92일이고
  위반은 400이다. `InventoryQueryService.list()`가 이미 집계하는
  `capacity`·`held`·`confirmed`·`remaining`·`salesStatus`를 그대로 쓴다.
- **열**: `객실 유형 ID`, `객실 유형`, `숙박일`, `총량`, `보류`, `확정`,
  `잔여`, `판매 상태`, `최대 인원`. 첫 행에 헤더를 둔다.
- **빈 파일은 내려주지 않는다.** 재고가 없는 지점·기간이면 헤더만 있는
  CSV를 내려주고, 본사가 "데이터가 없다"는 것을 바로 알게 한다.
- SELECT만 사용하고 재고를 변경하지 않는다.

### CSV 업로드

- `POST /api/staff/hotels/{hotelId}/inventory/import`가 CSV 본문을 받아
  여러 객실 유형의 여러 날짜 재고를 한 번에 바꾼다. `HQ_ADMIN`만 허용하고
  지점 직원은 403, 잘못된 세션은 401, 멱원 키 누락은 400, 없는 지점은
  404다.
- **내보낸 CSV를 그대로 다시 올릴 수 있어야 한다.** 헤더 행은 무시하고,
  열 순서는 내보내기와 같다. 이것이 본사가 CSV를 수정해서 다시 올리는
  기본 흐름이다.
- **총량 열만 반영한다.** `보류`·`확정`·`잔여`·`판매 상태`는 읽기 전용이다.
  업로드가 이 값을 바꾸면 이미 확정된 예약과 재고가 어긋난다.
  내보내기 열은 본사가 참고용으로 보는 것이지 입력이 아니다.
- **값 검증은 기존 `PATCH .../inventory`와 같은 기준을 쓴다.**
  총량은 0 이상 1,000 이하, 없는 객실 유형·다른 지점의 유형은 404,
  시드되지 않은 일자는 404 `INVENTORY_DAY_NOT_FOUND`, 확정·보류 건수
  아래로 내리면 409 `INVENTORY_CAPACITY_CONFLICT`로 거부하고
  **아무것도 바꾸지 않는다**.
- **한 파일의 모든 행을 한 트랜잭션에 처리한다.** 100행 중 99행만
  성공하고 1행이 409로 거부되면 본사가 어느 날짜까지 반영됐는지
  알 수 없다. 전부 성공하거나 전부 실패한다.
- **행 수 제한은 1,000행이다.** 92일 × 4유형 = 368행이 현실적인
  최대 규모다. 1,000행은 그 여유를 두고, 그 이상은 400으로 거부한다.
- **형식 오류는 400으로 거부한다.** 헤더가 없거나, 열 수가 다르거나,
  날짜·총량이 숫자가 아니거나, 빈 행이 중간에 있으면 400이다.
  이때도 아무것도 바꾸지 않는다.
- 멱원은 두 갈래로 동작한다. 같은 `Idempotency-Key` 재호출은 200에
  `created=false`로 같은 결과를 돌려주고, 응답 유실 뒤 새 키로 같은
  내용을 보내도 `staff_id`·지점·본문의 SHA-256 지문이 같아 같은
  결과를 돌려준다. 기존 `inventory_command`를 재사용한다.
- 응답은 `InventoryImportResponse(hotelId, totalRows, appliedRows,
  skippedRows, days, created)`다. `skippedRows`는 헤더·빈 행 수다.

## 마이그레이션 변경

- **새 마이그레이션이 필요 없다.** `inventory_command` 표가 이미
  `hotel_id`·`staff_id`·`room_type_id`·`idempotency_key`·
  `request_hash`를 가지고 있다. CSV 본문 전체가 요청 지문의 입력이
  되므로 같은 파일을 다시 올리면 같은 지문이 나온다.
- 기존 표를 변경하지 않는다.

## 관리자 UI 변경

- `재고·가격` (`/dashboard/inventory`)에 `CSV 내보내기` 버튼을
  추가한다. 브라우저에서 파일로 내려주고 UTF-8 BOM을 붙여
  엑셀이 한글을 깨지지 않게 읽게 한다 (감사 이력·운영 통계와
  같은 패턴).
- `CSV 업로드` 버튼과 대화상자: 파일을 고르면 **본문을 미리 보여주고**
  몇 행인지 센 뒤에 올릴 수 있게 한다. 서버 검증 실패 시
  대화상자를 닫지 않고 이유를 보여준다 (기존 패턴).
- **업로드는 매번 새 멱원 키를 쓴다** (다른 본사 버튼과 같은 패턴).
- `staff-api.ts`에 `exportInventoryCsv`·`importInventoryCsv`를
  추가한다. 403·404·409 메시지를 구분한다.

## 완료 기준

1. 내보낸 CSV를 수정하지 않고 그대로 다시 올리면 같은 재고가 유지된다.
2. 날짜별로 다른 총량을 한 파일로 반영할 수 있다.
3. 총량을 확정·보류 건수 아래로 내리는 행이 하나라도 있으면
   전체를 거부하고 아무것도 바꾸지 않는다.
4. 보류·확정·잔여·판매 상태 열은 무시된다.
5. 헤더 없음·열 수 불일치·숫자 아님·빈 행이면 400으로 거부한다.
6. 멱원 재호출이 같은 결과를 돌려주고 재고가 두 번 바뀌지 않는다.
7. 1,000행 초과면 400이다.
8. 기존 `PATCH .../inventory` 호출이 깨지지 않는다.

## 미검증 항목 (사전 명시)

- **라이브 DB·compose 재빌드·브라우저 확인은 실행하지 않는다.**
  라이브 재고를 본사가 임의로 바꾸면 고객 가용성에 즉시 영향을
  주므로 새 마이그레이션이 없더라도 사용자가 확인한다.
- **엑셀(.xlsx) 형식은 지원하지 않는다.** CSV만 지원한다.
  엑셀에서 CSV로 내보낸 파일은 BOM이 없으면 한글이 깨지므로
  BOM을 붙여서 내보내고, 업로드는 BOM 유무에 관계없이 받는다.
- **부분 성공은 허용하지 않는다.** 전부 성공하거나 전부 실패하는
  것이 완료 기준 3번이다.   "실패한 행만 무시하고 나머지 적용"은
  본사가 어느 날짜가 반영됐는지 알 수 없어서 뺐다.
- **AI 예약 컨시어지의 추천이 바뀐 재고를 다루는지 확인하지 않는다.**
  AI는 가용성을 읽으므로 재고가 바뀌면 오퍼가 따라 바뀌지만
  컨시어지 프롬프트 동작을 직접 검증하지는 않는다.
- **판매 중지 구간이 있는 날짜의 총량도 올릴 수 있다.** 중지는
  총량과 별개이므로 중지 중인 날짜의 재고를 미리 정비하는 것은
  허용한다.
