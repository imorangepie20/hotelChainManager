# 고객 웹 Playwright 기준선 복구와 카탈로그 쓰기 기능 감사 계획

## 목적

- 기록된 고객 웹 Playwright 실패 5건을 현재 코드에서 재현하고 테스트 결함과 실제 제품 결함을 분리한다.
- 결제 모드와 서버가 반환한 Toss 클라이언트 키 환경이 다를 때 외부 SDK를 불러오기 전에 차단한다.
- 관리자 로드맵의 호텔·객실 및 재고·가격 쓰기 기능이 API·UI·E2E에 실제로 연결돼 있는지 대조하고, 확인된 누락만 구현한다.

## 사용자 여정

1. 고객은 필수 예약자 정보를 모두 입력한 뒤 영문 화면에서도 테스트 결제를 완료하고 새로고침 후 확정 상태를 본다.
2. 고객은 예약 변경 결제 화면에서 기존 예약과 변경 예약을 함께 확인한다.
3. 고객은 적용 중인 예약 변경이 완료되면 최신 객실과 취소 미리보기를 본다.
4. 모바일·키보드 사용자는 결제 버튼을 한 번만 실행하고 충분한 터치 높이를 보장받는다.
5. 결제 모드와 클라이언트 키 환경이 다르면 브라우저는 Toss SDK를 내려받지 않고 안전한 오류를 표시한다.
6. 본사 관리자는 호텔·객실과 재고·가격 화면에서 로드맵에 기록된 모든 쓰기 동작을 실행할 수 있다.

## 구현 순서와 완료 기준

1. 고객 웹 전체 Playwright를 격리된 로컬 서버에서 실행해 5건 RED를 재현한다.
2. 현재 계약과 어긋난 테스트 픽스처·셀렉터·타이밍을 결정적으로 고치고, 결제 모드/키 불일치 단위 계약을 추가한다.
3. 단위 계약과 live 키 E2E가 제품 결함 때문에 RED임을 확인한다.
4. 결제 모드/키 일치 검사를 SDK 로드 전에 적용하고 대상 테스트를 GREEN으로 만든다.
5. 대상 E2E를 반복 실행하고 고객 웹 전체 Playwright·타입·빌드를 통과시킨다.
6. 호텔·객실 및 재고·가격의 로드맵 항목을 API·UI·테스트에 매핑한다. 누락이 있으면 별도 RED부터 추가하고 최소 구현한다.

## 안전 경계

- 모든 고객 결제·예약 테스트는 로컬 브라우저와 가짜 API 응답만 사용한다.
- 운영 결제, 운영 예약, 운영 DB에는 변경 요청을 보내지 않는다.
- 호텔 가격·재고 권한은 계속 Spring Boot에 두고 UI는 서버 명령 API만 호출한다.
