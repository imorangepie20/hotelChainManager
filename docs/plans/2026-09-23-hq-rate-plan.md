# 본사 객실 유형 관리 - 두 번째 요금제 등록·수정 (2026-09-23)

> 상태: 작업 트리에만 있고 커밋하지 않은 상태.

## 변경 이유

`admin-menu-roadmap.md` 1번 `지점·객실 유형 관리`의 마지막 남은 항목이다.
객실 유형 하나에 **요금제가 무조건 1개**다. `RoomTypeCommandService`가 유형을
만들 때 `기본 요금제`를 1개 심는 것이 전부고, 본사가 요금제를 직접 만들거나
고치는 수단이 없다.

이것이 실제로 빠뜨리는 운영 동작:

1. **같은 객실을 조식 포함·미포함으로 따로 팔 수 없다.** 조식 여부는 유형 생성
   시점에 한 번 정해지고, `PATCH .../room-types/{id}`로 바꾸면 확정 예약의
   계약 조건이 바뀌기 때문에 409 `ROOM_TYPE_BREAKFAST_CONFLICT`로 거부한다.
   현실에서는 "조식 포함 120,000원"·"조식 미포함 95,000원"을 **같은 객실에서
   동시에** 팔아야 한다.
2. **다른 취소 규정을 가진 요금을 만들 수 없다.** `rate_plan.policy_version`이
   시드값 `FLEX-2026-01`으로 고정이다. 유연한 요금(무료 취소)과 확정 요금
   (환불 불가)을 한 객실에서 함께 내놓을 수 없다.
3. **일자별 요금을 요금제 단위로 관리할 수 없다.** `PATCH .../rates`가
   "기본 요금제" 1개를 암묵적으로 선택한다. 두 번째 요금제가 생기면 어느
   요금제의 금액을 바꾸는지 지정할 방법이 없다.

`AvailabilityService`는 이미 `JOIN rate_plan`으로 **모든** 요금제를 읽어서
요금제별로 오퍼를 만든다. 그러므로 두 번째 요금제를 심기만 하면 고객
검색에 즉시 별도 오퍼로 나타난다. 빌드할 것은 "본사가 요금제를 만드는
수단"이지, 가용성 파이프라인이 아니다.

## 서버 변경

### 요금제 생성

- `POST /api/staff/hotels/{hotelId}/room-types/{roomTypeId}/rate-plans`가
  새 요금제를 만든다. `HQ_ADMIN`만 허용하고 지점 직원은 403, 잘못된 세션은 401,
  멱원 키 누락은 400, 없는 지점·다른 지점의 유형·없는 유형은 404다.
- 본문: `name`(1~100자)·`breakfastIncluded`·`policyVersion`(1~50자)·
  `defaultRateKrw`(0~10,000,000원)·`fromDate`(선택, 기본값은 지점 현지 시간대
  기준 오늘)·`days`(1~92, 기본값 90). 위반은 400이다.
- **요금제 행과 일자별 금액을 같은 트랜잭션에 심는다.** 유형 시드와 같은
  원칙이다. 실패하면 요금제 행도 롤백돼서 "요금제는 있는데 금액이 없어
  오퍼가 안 나오는" 상태가 생기지 않는다.
- **재고는 심지 않는다.** 재고는 객실 유형 단위(`inventory_day`의 PK가
  `room_type_id` + `stay_date`)다. 요금제는 같은 재고를 공유한다. 그러므로
  요금제 생성이 재고를 만들면 같은 일자의 재고가 충돌하고, 유형의 재고를
  덮어쓰는 부작용이 생긴다. `ON CONFLICT DO NOTHING`으로 재고가 이미 있으면
  그대로 둔다.
- **시드 범위를 벗어난 날짜는 거부한다.** 요금제가 심는 금액은
  `inventory_day`가 가진 일자 안에 있어야 오퍼가 성립한다.
  `inventory_day`에 없는 날짜를 요청하면 409 `INVENTORY_DAY_NOT_FOUND`다.
  이것은 재고가 없는 날짜의 금액을 만들어놓고 고객에게 보여주지 않는
  쓸모없는 요금제를 막는다.
- **정책 버전을 취소 규정과 연결한다.** `policy_version`은 예약의
   `policy_snapshot`에 그대로 들어간다. 값을 검증만 하고 해석하지는 않는다.
   나중에 본사가 `FLEX-2026-01`과 `NONREFUNDABLE-2026-01`을 구분해 취소
   규정을 매핑할 때 이 값이 기준이 된다.
- 멱원은 두 갈래로 동작한다. 같은 `Idempotency-Key` 재호출은 200에
  `created=false`로 같은 요금제를 돌려주고, 응답 유실 뒤 새 키로 같은 내용을
  보내도 `staff_id`·지점·유형·이름·조식·정책·금액·시작일·일수의 SHA-256 지문이
  같아 같은 결과를 돌려준다.
- 응답은 `RatePlanCreateResponse(ratePlanId, hotelId, roomTypeId, name,
  breakfastIncluded, policyVersion, defaultRateKrw, seededDays, created)`다.

### 요금제 이름 수정

- `PATCH /api/staff/hotels/{hotelId}/room-types/{roomTypeId}/rate-plans/{ratePlanId}`
  이 이름만 바꾼다. 응답은 200이고 멱원 재호출은 `changed=false`로 같은
  결과를 돌려준다.
- **조식 포함 여부·정책 버전은 이 API로 바꾸지 않는다.** 둘 다 확정 예약의
  계약 조건이어서 기존 `PATCH .../room-types/{id}`와 같은 이유로 409가 난다.
  요금제의 계약 조건을 바꾸려면 요금제를 새로 만드는 것이 맞다. 이것이
  "두 번째 요금제"를 만드는 이유다.
- **실제로 바꾸는 값이 없으면 DB를 건드리지 않고 멱원 기록만 남긴다.**
- 이름 중복은 **같은 유형 안에서만** 검사한다. 다른 유형·다른 지점의 같은
  이름은 허용한다. 요금제 이름은 유형 안에서 구별되면 충분하다.
  위반은 409 `RATE_PLAN_NAME_CONFLICT`다.

### 요금제 조회

- `GET /api/staff/hotels/{hotelId}/room-types/{roomTypeId}/rate-plans`가
  유형의 전체 요금제를 돌려준다. SELECT만 사용한다. `HQ_ADMIN`·
  `BRANCH_STAFF` 모두 자기 지점을 읽을 수 있다. 본사는 다른 지점도 읽는다.
- 카탈로그 본문이 이미 `RoomTypeCatalogView.ratePlans`로 모든 요금제를
  내려주고 있으므로 **이 응답은 요금제 화면용 단독 조회**다.

### 일자별 요금 변경의 요금제 선택

- `PATCH .../rates`가 선택적 `ratePlanId`를 본문에 받는다.
  **명시하지 않으면 지금과 같이 기본 요금제**를 쓴다. 기존 호출은
  그대로 동작한다.
- **요청한 요금제가 유형에 속하지 않으면 404**다. 다른 유형의 요금제
  금액을 바꾸는 것을 막는다. 기존 404 `ROOM_TYPE_RATE_PLAN_NOT_FOUND`를
  재사용한다.
- `GET .../rates`도 같은 선택자를 쿼리 파라미터로 받는다.

## 마이그레이션 변경

- V62 additive 마이그레이션이 `rate_plan_command` 표를 만든다.
  `rate_plan`이 `room_type`을 참조하므로 `rate_plan_id`는 NOT NULL이다.
  유형 삭제 시 참조가 끊기지 않게 `ON DELETE CASCADE`는 쓰지 않는다.
- `(hotel_id, staff_id, idempotency_key)` 유일 인덱스로 같은 멱원 키의
  중복 처리를 막고, `(hotel_id, staff_id, request_hash)` 유일 인덱스로
  같은 내용 재시도의 중복 처리를 막는다. 기존 `room_type_command`·
  `rate_command`와 같은 구조다.
- **기존 표를 변경하지 않는다.** 라이브 DB의 3개 지점·4개 유형은
  영향을 받지 않는다.

## 관리자 UI 변경

- `호텔 및 객실` (`/dashboard/hotels`)의 객실 유형 표에 **요금제 열**을
  추가한다. 카탈로그 응답의 `ratePlans`를 보여준다. 유형마다 여러 요금제가
  있을 수 있으므로 **유형 표 아래에 각 유형의 요금제를 나열**한다.
- `요금제 추가` 버튼과 대화상자: 이름·조식 포함 여부·정책 버전·기본 요금·
  시작일·일수. 시작일·일수의 기본값을 채운다. 서버 검증 실패 시
  대화상자를 닫지 않고 안내를 보여준다 (기존 패턴).
- `요금제 이름 수정` 버튼과 대화상자: 현재 이름으로 미리 채운다.
- **생성·수정은 매번 새 멱원 키를 쓴다** (중지·재개·삭제 버튼과 같은 패턴).
- 금액 입력은 `type="text"` + `inputMode="numeric"`을 쓴다
  (공통 정책·객실 유형·재고 화면과 같은 이유).
- `staff-api.ts`에 `listRatePlans`·`createRatePlan`·`renameRatePlan`을
  추가한다. 403·404·409 메시지를 구분한다.

## 완료 기준

1. `POST`가 요금제와 일자별 금액을 한 트랜잭션에 심고, 고객
   `GET /api/availability`에 새 요금제 오퍼가 즉시 나타난다.
2. 재고 없는 날짜의 금액을 거부하고, 재고를 덮어쓰지 않는다.
3. 멱원 재호출이 같은 결과를 돌려주고, 다른 내용이면 409가 난다.
4. `PATCH .../rates`가 요금제를 명시적으로 선택할 수 있고,
   선택하지 않으면 기본 요금제를 쓴다.
5. 이름 중복이 같은 유형 안에서만 409가 난다.
6. 관리자 UI에서 추가·이름 수정이 서버 검증 실패 시 대화상자를
   닫지 않는다.
7. 기존 API 호출이 깨지지 않는다 (`ratePlanId` 선택적).

## 미검증 항목 (사전 명시)

- **라이브 DB·compose 재빌드·브라우저 확인은 실행하지 않는다.**
  V62가 라이브에 적용되지 않았으므로 실제 요금제 흐름은 사용자가 확인한다.
- **정책 버전 문자열의 비즈니스 의미는 검증하지 않는다.** 서버는 길이만
  검사한다. `NONREFUNDABLE-2026-01`이 실제로 환불 불가로 동작하는지는
  취소 규정 매핑이 없으므로 확인할 수 없다. 이것은 후속 항목이다.
- **두 요금제의 재고가 공유되는 것의 영향은 설계만 하고 라이브로
  확인하지 않는다.** 한 요금제로 예약이 확정되면 다른 요금제의
  남은 객실 수도 줄어든다. 이것이 의도된 동작이다.
- **AI 예약 컨시어지의 추천이 새 요금제를 다루는지 확인하지 않는다.**
  AI는 가용성을 읽으므로 오퍼가 늘어나는 것을 보게 되지만 컨시어지
  프롬프트 동작을 직접 검증하지는 않는다.
- **요금제 삭제는 이번 범위가 아니다.** 예약·예약 변경 요청이 요금제를
  참조하므로 객실 유형 삭제가 취한 것과 같은 충돌 검사가 필요하다.
