# 본사 재고·가격 - 판매 중지 구간 설정 (2026-09-24)

> 상태: 작업 트리에만 있고 커밋하지 않은 상태.

## 변경 이유

`admin-menu-roadmap.md` 2번 `재고·가격`의 남은 항목 중 "판매 중지 구간
설정"을 구현한다. 1번 영역이 완료됐으므로 로드맵 순서(1 → 2 → 3 → 5 →
4 → 7 → 6 → 8)에 따라 2번의 남은 항목으로 넘어간다.

현재 본사가 특정 날짜의 판매를 멈추는 유일한 수단은 `PATCH .../inventory`
로 **해당 일자의 총량을 0으로 내리는 것**이다. 이것은 동작하지만 세 가지
운영 문제가 있다.

1. **원래 총량을 잃어버린다.** 리모델 공사·단기 매뉴언 점검으로 9월 25일~9월
   27일 판매를 멈추려면 총량을 0으로 덮어써야 한다. 복구하려면 본사가
   "원래 8실이었다"는 것을 **기억하고 있어야** 한다. 재조정 대화상자는
   표시된 전체 일자를 한 번에 같은 값으로 덮기 때문에, 공사 전날의 8실과
   공사 기간의 0실을 **한 요청으로 동시에 보낼 수도 없다**.
2. **매진과 판매 중지를 구분할 수 없다.** 둘 다 `remaining = 0`이다.
   고객 화면은 물론이고 직원 재고 화면도 "매진"이라고만 보여서, 본사가
   의도적으로 멈춘 구간인지 실제로 다 팔린 것인지 알 수 없다.
3. **재고 0은 확정·보류 건수 때문에 내릴 수 없다.** 이미 확정 예약이
   있는 날짜의 총량은 409 `INVENTORY_CAPACITY_CONFLICT`로 거부된다.
   그래서 **판매를 멈추고 싶은 날짜에 이미 예약이 있으면 멈출 수
   없다.** 이것은 재고 총량의 무결성 제약이 맞지만, "공사 구간의 신규
   판매를 멈추고 기존 예약은 별도 처리한다"는 본사의 의도를 담을 수
   없다는 뜻이기도 하다.

그래서 **총량과 별개의 판매 중지 상태**를 둔다. 지점 전체 판매 중지
(`PATCH /api/staff/hotels/{hotelId}/active`)와 같은 원칙으로, 중지는
**신규 판매만 막고 기존 예약을 그대로 둔다**.

## 서버 변경

### 판매 중지 구간 설정

- `PATCH /api/staff/hotels/{hotelId}/room-types/{roomTypeId}/sales-status`가
  객실 유형의 날짜 구간 판매 상태를 바꾼다. `HQ_ADMIN`만 허용하고 지점
  직원은 403, 잘못된 세션은 401, 멱원 키 누락은 400, 없는 지점·다른
  지점의 유형·없는 유형은 404다.
- 본문: `fromDate`·`toDate`(필수)·`status`(`OPEN`·`STOPPED` 중 하나).
  위반은 400이다. 기간은 최대 92일이고 역순은 400이다.
- **총량은 건드리지 않는다.** `capacity`·`held`·`confirmed`를 그대로
  둬서 공사 뒤 원래 재고가 돌아오게 한다. 이것이 총량 0과의 핵심 차이다.
- **중지한 구간에 이미 확정·보류된 예약은 그대로 둔다.** 지점 전체 중지와
  같은 원칙이다. 취소는 전용 API가 있고, 중지가 예약을 취소하면 본사가
  고객에게 알리지 않은 채 환불 의무가 생긴다.
- **판매 중지는 신규 오퍼 생성만 막는다.** `AvailabilityService`가
  중지한 일자를 포함하는 검색에서 해당 유형의 오퍼를 빼서, 고객이
  "예약 가능한 객실이 없습니다"를 보게 한다. 오류가 아니다.
- **중지 구간 조회는 직원만 한다.** `GET /api/staff/hotels/{hotelId}/
  room-types/{roomTypeId}/sales-status`가 유형의 중지 구간을
  최신순으로 돌려준다. `HQ_ADMIN`·`BRANCH_STAFF` 모두 자기 지점을
  읽을 수 있다. SELECT만 사용한다.
- 멱원은 두 갈래로 동작한다. 같은 `Idempotency-Key` 재호출은 200에
  `created=false`로 같은 구간을 돌려주고, 응답 유실 뒤 새 키로 같은
  내용을 보내도 `staff_id`·지점·유형·시작일·종료일·상태의 SHA-256
  지문이 같아 같은 결과를 돌려준다. **이미 같은 상태면 DB를 건드리지
  않고 멱원 기록만 남긴다.**
- 응답은 `SalesStatusResponse(hotelId, roomTypeId, fromDate, toDate,
  status, stoppedDays, created)`다.

### 재고 조회에 판매 상태 노출

- `InventoryView`의 각 일자에 `salesStatus`(`OPEN`·`STOPPED`)를
  추가한다. SELECT만 추가하므로 재고를 변경하지 않는다.
- 직원 재고 화면이 "매진"과 "판매 중지"를 구분하게 한다.

## 마이그레이션 변경

- V63 additive 마이그레이션이 `room_type_sales_status` 표를 만든다.
  `(room_type_id, stay_date)`에 `status`를 둔다.
- `(hotel_id, staff_id, idempotency_key)` 유일 인덱스로 같은 멱원 키의
  중복 처리를 막고, `(hotel_id, staff_id, request_hash)` 유일 인덱스로
  같은 내용 재시도의 중복 처리를 막는다. 기존 `inventory_command`·
  `room_type_command`와 같은 구조다.
- **기존 표를 변경하지 않는다.** 라이브 DB의 3개 지점·4개 유형은
  영향을 받지 않는다. 모든 날짜가 `OPEN`이므로 고객 가용성도
  바뀌지 않는다.

## 관리자 UI 변경

- `재고·가격` (`/dashboard/inventory`)의 그리드에 `판매 중지` 열을
  추가한다. 각 유형의 셀에 중지한 날짜가 있으면 "중지"로 표시한다.
- `판매 중지` 버튼과 대화상자: 시작일·종료일. 기본값을 현재 보이는
  범위의 첫날·마지막 날로 채운다. **매진 셀과 중지 셀의 색을 다르게** 해서
  본사가 의도적인 중지와 실제 매진을 구분하게 한다.
- `판매 재개` 버튼: 중지한 구간의 상태를 `OPEN`으로 돌린다.
- **생성·수정은 매번 새 멱원 키를 쓴다** (다른 본사 버튼과 같은 패턴).
- 날짜 입력은 `type="date"`를 쓴다 (기존 범위 입력과 같은 패턴).
- `staff-api.ts`에 `getSalesStatus`·`setSalesStatus`를 추가한다.
  403·404·409 메시지를 구분한다.

## 완료 기준

1. `PATCH`가 날짜 구간의 판매 상태를 바꾸고 **총량은 그대로** 둔다.
2. 중지한 구간에 확정 예약이 있어도 중지가 가능하다 (신규 판매만 막음).
3. 고객 `GET /api/availability`가 중지한 구간을 포함하는 검색에서
   해당 유형의 오퍼를 내놓지 않는다.
4. 멱원 재호출이 같은 결과를 돌려주고, 다른 내용이면 409가 난다.
5. 기간 검증(최대 92일, 역순 400)이 동작한다.
6. 관리자 UI에서 중지·재개가 서버 검증 실패 시 대화상자를 닫지 않는다.
7. 재고 화면이 "매진"과 "판매 중지"를 구분해서 보여준다.
8. 기존 재고 API 호출이 깨지지 않는다 (`salesStatus`는 추가 필드).

## 미검증 항목 (사전 명시)

- **라이브 DB·compose 재빌드·브라우저 확인은 실행하지 않는다.**
  V63이 라이브에 적용되지 않았으므로 실제 중지 흐름은 사용자가 확인한다.
- **중지한 구간의 기존 예약에 대한 고객 안내는 이번 범위가 아니다.**
  중지가 예약을 취소하지 않으므로 본사가 기존 예약을 어떻게 처리할지는
  별도 정책이 필요하다.
- **재고 일괄 업로드(CSV)는 다음 항목이다.** 2번의 마지막 남은 항목이다.
- **판매 중지 구간의 요금은 그대로 둔다.** 중지가 요금을 건드리면
  재개 뒤 복구할 수 없으므로 총량과 같은 이유로 건드리지 않는다.
